# 오픈매트 이미지 기능 기획서

작성일: 2026-06-11
대상: Rolling Flutter 앱, Rolling API
브랜치 기준: `codex/openmat-image-create-read`
범위: 오픈매트 생성/수정 시 이미지 최대 3장 추가, 오픈매트 조회 시 이미지 노출, 운영환경 안전 배포

## 1. 문서 목적

- 현재 오픈매트는 제목, 설명, 장소, 좌표 중심으로만 작성되고 있어 현장 분위기나 공간 정보를 시각적으로 전달하지 못한다.
- 이번 문서는 오픈매트에 이미지를 최대 3장까지 붙이고 조회에서 다시 볼 수 있게 하는 기능의 제품 범위와 운영 안전한 도입 순서를 정의한다.
- 특히 운영환경에서 기존 오픈매트 생성/조회 흐름을 깨지 않는 additive migration과 롤아웃 방식을 우선한다.

## 2. 현재 상태와 문제

### 현재 상태

- 오픈매트 생성 API는 텍스트 정보와 좌표 정보만 저장한다.
- 오픈매트 목록/상세 조회 응답에는 이미지 필드가 없다.
- 이미지 업로드는 커뮤니티, 훈련일지, 대회 포스터에서 S3 presigned URL + 공개 URL 저장 패턴을 이미 사용 중이다.
- 오픈매트는 비로그인 사용자도 목록/상세를 볼 수 있는 공개 소비 흐름이 포함되어 있다.

### 문제

- 사용자는 장소 규모, 매트 환경, 주차/입구 분위기 같은 정보를 텍스트만으로 판단해야 한다.
- 호스트는 설명을 길게 써도 신뢰를 높이기 어렵고, 신규 참여자는 참석 결정을 미루기 쉽다.
- 운영 관점에서는 기능 추가 과정에서 기존 오픈매트 조회/생성, 지도, 신청, 상태 스케줄러 흐름을 건드리면 안 된다.

## 3. 대상 사용자

- 오픈매트를 처음 열어보는 참가자
- 오픈매트를 개설하는 호스트
- 운영환경 안정성과 배포 리스크를 관리해야 하는 백엔드/앱 팀

## 4. 제품 목표

- 호스트는 오픈매트 생성/수정 시 이미지를 최대 3장까지 첨부할 수 있다.
- 사용자는 오픈매트 조회 시 첨부된 이미지를 확인할 수 있다.
- 기존 이미지 없는 오픈매트와 구버전 앱은 깨지지 않는다.
- 운영 배포는 기존 API 계약을 대체하지 않고 additive change로 반영된다.

## 5. 범위 경계

### 지금 출시할 범위

- 오픈매트 생성 시 이미지 URL 목록 저장
- 오픈매트 수정 시 이미지 추가/교체/삭제
- 오픈매트 상세 조회 시 이미지 목록 응답
- 현재 `OpenMatResponse`가 목록/상세에 공용으로 쓰이므로, 이번 출시에서는 목록/상세 응답 모두에 `imageUrls`를 additive field로 포함하는 계약으로 확정한다
- Flutter 노출 범위는 이번 출시에서 상세 우선으로 제한하고, 목록 썸네일 활용은 후속으로 미룬다
- 이미지 업로드용 presigned URL 발급 API
- 최대 3장 제한, 순서 보존, 빈 값/잘못된 URL 검증
- 기존 이미지 없는 데이터 fallback

### 이번 범위에서 제외

- 이미지 편집 기능
- 이미지 캡션, alt text, 대표 이미지 수동 지정
- 이미지 신고/검수/모더레이션 운영 화면
- 이미지 좋아요, 확대 뷰 분석, 조회수 추적
- 기존 오픈매트 데이터 일괄 백필

## 6. 선택지 평가

### 선택지 A. `open_mats`에 `image_urls_json` 컬럼 추가

- 장점
- 가장 작은 DB 변경이다.
- 기존 `open_mats` 읽기/쓰기 흐름 안에서 처리할 수 있다.
- 최대 3장 제한에서는 저장 구조가 충분히 단순하다.
- 기존 훈련일지의 다중 이미지 확장 방식과 유사한 패턴을 재사용할 수 있다.

- 단점
- 이미지별 메타데이터 확장성이 낮다.
- 장기적으로 운영용 이미지 상태값이나 대표 이미지 정책이 필요해지면 구조 변경 여지가 있다.

### 선택지 B. `open_mat_images` 별도 테이블 추가

- 장점
- 정렬 순서, 대표 이미지, 검수 상태 같은 메타데이터 확장이 쉽다.
- 관계형 모델이 더 명확하다.

- 단점
- 엔티티, 조회 전략, 테스트, 마이그레이션 표면적이 더 넓다.
- 현재 요구사항 대비 구현/운영 복잡도가 높다.

### 권장안

- 지금은 선택지 A를 권장한다.
- 이유는 이번 요구사항이 `최대 3장`, `생성/수정/조회`, `운영 안정성 우선`에 집중되어 있기 때문이다.
- 별도 이미지 메타데이터 요구가 없고, 기존 데이터를 건드리지 않는 additive migration이 가장 중요하므로 JSON 컬럼 방식이 현재 목표에 가장 적합하다.
- 추후 운영 요구가 커지면 별도 테이블로 승격하는 방향을 다음 단계 후보로 남긴다.

## 7. 제품 권장안

### 지금

- 오픈매트 이미지 저장 필드를 additive 하게 추가한다.
- 클라이언트는 presigned URL로 S3에 직접 업로드한 뒤 공개 `imageUrl` 목록만 서버에 저장한다.
- 생성/수정 request에 `imageUrls`를 추가한다.
- 목록/상세 공용 응답 DTO에 `imageUrls`를 additive 하게 추가한다.
- 기존 오픈매트 조회 응답에서 이미지가 없으면 빈 배열로 응답한다.
- 수정 API는 `필드 미전달 = 유지`, `빈 배열 = 전체 삭제`, `null = 400`으로 확정한다.
- 저장 가능한 URL은 오픈매트 이미지 업로드 API가 발급한 S3 공개 URL prefix만 허용한다.

### 다음

- 목록 카드에서 첫 번째 이미지를 활용한 썸네일 노출 여부를 검토한다.
- 이미지 업로드 실패율과 첨부 사용률을 보고 대표 이미지 정책 필요성을 판단한다.

### 나중

- 이미지 모더레이션
- 관리자 보정/삭제 도구
- 별도 `open_mat_images` 테이블 전환 검토

## 8. 핵심 사용자 흐름

### 오픈매트 생성

1. 호스트는 오픈매트 생성 화면에서 기본 정보 입력 후 이미지를 최대 3장 선택한다.
2. 앱은 각 이미지에 대해 업로드 URL을 발급받고 S3에 직접 업로드한다.
3. 업로드가 끝나면 앱은 생성 API에 공개 `imageUrls` 목록을 포함해 저장 요청을 보낸다.
4. 서버는 이미지 URL 목록을 검증하고 저장한다.
5. 생성 완료 응답에서 저장된 이미지 목록을 다시 내려준다.

### 오픈매트 수정

1. 호스트는 기존 오픈매트의 이미지 목록을 본다.
2. 이미지를 유지, 교체, 삭제하거나 새 이미지를 추가한다.
3. 앱은 최종 이미지 순서를 기준으로 `imageUrls`를 다시 보낸다.
4. 서버는 최종 목록 기준으로 저장 상태를 교체한다.

### 오픈매트 조회

1. 사용자는 오픈매트 상세에 진입한다.
2. 서버 응답의 `imageUrls`가 있으면 앱은 이미지 캐러셀 또는 갤러리로 보여준다.
3. `imageUrls`가 비어 있으면 기존처럼 텍스트/지도 정보만 보여준다.

## 9. API/계약 권장 방향

### 생성 요청

`OpenMatCreateRequest`에 추가 권장:

```json
{
  "imageUrls": [
    "https://cdn.rolling.com/openmats/images/a.jpg",
    "https://cdn.rolling.com/openmats/images/b.jpg"
  ]
}
```

정책:

- 미전달 또는 `null`이면 이미지 없음으로 처리한다.
- 최대 3장까지 허용한다.
- 순서를 보존한다.
- 빈 문자열, 중복 URL, 비정상 URL은 거부한다.

### 수정 요청

`OpenMatUpdateRequest`에 추가 권장:

```json
{
  "imageUrls": [
    "https://cdn.rolling.com/openmats/images/a.jpg",
    "https://cdn.rolling.com/openmats/images/c.jpg"
  ]
}
```

수정 정책:

1. `imageUrls` 필드가 요청 body에 없음
- 기존 이미지를 유지한다.

2. `imageUrls: []`
- 기존 이미지를 모두 제거한다.

3. `imageUrls: null`
- `400 VALIDATION_ERROR`를 반환한다.
- 이유는 `null`을 허용하면 일부 클라이언트 직렬화 방식에서 의도치 않은 전체 삭제가 발생할 수 있기 때문이다.
- 이 계약을 위해 서버는 `@JsonSetter` 기반 field-present 패턴으로 `미전달`과 `null`을 구분해야 한다.

### 조회 응답

`OpenMatResponse`에 추가 권장:

```json
{
  "imageUrls": [
    "https://cdn.rolling.com/openmats/images/a.jpg",
    "https://cdn.rolling.com/openmats/images/b.jpg"
  ]
}
```

응답 정책:

- 이미지가 없으면 `[]`를 반환한다.
- 기존 앱이 새 필드를 무시해도 동작해야 한다.
- 현재 구조상 목록과 상세가 같은 `OpenMatResponse`를 사용하므로, 이번 출시에서는 둘 다 `imageUrls`를 포함한다.
- 목록 payload 증가는 최대 3장 제한으로 관리하고, 목록 UI에서 실제 노출은 후속 판단으로 미룬다.

### 업로드 URL 발급 API

권장 endpoint:

```text
POST /api/v1/open-mats/image-upload-url
```

정책:

- 인증 사용자만 호출 가능
- 허용 MIME 타입과 확장자 제한
- 업로드 대상 prefix는 `openmats/images/`
- 응답은 `uploadUrl`, `imageUrl`을 포함
- 이미지 파일 자체는 서버를 거치지 않고 클라이언트가 S3에 직접 업로드
- 생성/수정 API는 이 endpoint가 발급한 S3 공개 URL prefix와 일치하는 URL만 저장 허용
- 임의 외부 URL, 다른 도메인 URL, 다른 prefix URL은 거부

## 10. 데이터 모델 권장 방향

### 권장 저장 모델

`open_mats`에 컬럼 추가:

- `image_urls_json TEXT NULL`

권장 이유:

- 기존 테이블에 nullable 컬럼 1개만 추가하면 된다.
- 기존 row 백필이 필요 없다.
- 기존 조회/수정 기능을 깨지 않는 범위에서 가장 작은 migration이다.

### 직렬화 정책

- 저장은 JSON 문자열 배열로 보관한다.
- 읽기 시 파싱 실패 또는 `null`이면 빈 배열로 fallback 한다.
- 저장 전 서버가 URL 정규화와 개수 검증을 수행한다.
- 저장 전 서버는 `cloud.aws.s3.public-base-url` prefix 검증을 수행한다.

## 11. 운영환경 안전한 마이그레이션/롤아웃

### 원칙

- 기존 API를 대체하지 않고 additive 하게 확장한다.
- 기존 데이터는 수정하지 않는다.
- 구버전 앱이 새 필드를 보내지 않아도 정상 동작해야 한다.
- 새 앱이 이미지 필드를 기대하더라도 이미지 없는 기존 데이터에서 깨지지 않아야 한다.

### 권장 배포 순서

1. DB migration 배포
- `open_mats.image_urls_json` nullable 컬럼 추가
- default 값이나 backfill 작업은 하지 않는다

2. 백엔드 1차 배포
- `imageUrls` 필드를 읽어도 되고 안 읽어도 되는 상태로 반영
- 응답에서는 이미지 없을 때 빈 배열 반환
- 업로드 URL 발급 API 추가
- 구버전 클라이언트 request와 완전 호환 유지

3. 앱 배포
- 새 앱에서만 업로드 UI와 `imageUrls` 저장 사용
- 조회 화면은 이미지가 없으면 기존 UI fallback

4. 운영 검증
- 신규 생성 데이터 몇 건으로 업로드/저장/상세 조회 확인
- 오류율, payload size, DB 예외 여부 모니터링

### 롤백 전략

- 앱에서 이미지 업로드 UI를 비활성화해도 기존 오픈매트 기능은 유지돼야 한다.
- 백엔드 장애 시 `imageUrls`를 빈 배열로 축소 반환해도 기존 핵심 흐름은 살아 있어야 한다.
- nullable additive 컬럼 방식이므로 긴급 시 기능만 비활성화하고 데이터는 남겨둘 수 있어야 한다.

## 12. 수용 기준

### 기능 수용 기준

- 호스트는 오픈매트 생성 시 이미지를 0장부터 3장까지 첨부할 수 있다.
- 4장 이상은 서버에서 거부된다.
- 호스트는 오픈매트 수정 시 기존 이미지를 유지, 제거, 교체할 수 있다.
- 목록/상세 조회 응답에는 저장된 이미지 순서대로 `imageUrls`가 포함된다.
- 이미지가 없는 기존 오픈매트 조회는 정상 응답한다.
- 임의 외부 URL은 저장되지 않는다.

### 운영 수용 기준

- migration은 기존 `open_mats` row를 rewrite 하거나 backfill 하지 않는다.
- 구버전 앱 생성/수정 요청은 배포 후에도 정상 처리된다.
- 비로그인 공개 조회에서 이미지 URL이 깨지지 않는다.
- 오픈매트 신청, 상태 스케줄러, 지도 좌표, 신고/가리기 기능 회귀가 없어야 한다.

## 13. 성공 신호

- 신규 오픈매트 중 이미지 첨부 비율이 의미 있게 나온다.
- 이미지가 있는 오픈매트의 상세 진입 후 신청 전환이 이미지 없는 오픈매트보다 개선되는지 관찰할 수 있다.
- 이미지 업로드 실패율이 낮고, 운영 장애 없이 배포가 완료된다.

## 14. 핵심 리스크와 완화

### 리스크 1. 구버전 앱과의 충돌

- 완화
- request는 새 필드 optional로 추가한다.
- response는 additive field만 추가한다.

### 리스크 2. 운영 배포 중 DB/코드 호환 문제

- 완화
- 먼저 nullable 컬럼만 추가한다.
- 컬럼 없이는 실행되지 않는 코드와 동시에 배포하지 않는다.

### 리스크 3. 잘못된 URL 또는 외부 임의 URL 저장

- 완화
- 서버에서 URL 포맷, 길이, 허용 host 또는 S3 public base URL prefix 검증을 한다.
- presigned 업로드 경로 기반 URL만 허용하는 방향을 권장한다.

### 리스크 4. 조회 payload 증가

- 완화
- 최대 3장으로 제한한다.
- 필요 시 후속 단계에서 목록과 상세 DTO를 분리한다.

## 15. 미해결 의사결정 항목

- `imageUrls: null`을 수정 API에서 비움으로 볼지, 오류로 볼지
  결정 완료: `null = 400`, `[] = 비움`, `필드 없음 = 유지`
- 이미지 업로드 후 미사용 파일 정리 정책을 둘지
  결정 권장: 백엔드 + 인프라, 후속 과제로 분리 가능
