# 관리자 사용자 제재 기획서

이 문서는 현재 Rolling 백엔드 기준으로, 관리자 기능에서 `사용자 제재`를 추가하기 위한 제품 기획서다.

핵심 목표는 단순히 계정을 막는 것이 아니라, 운영자가 문제 사용자를 `검색 -> 확인 -> 제재 -> 해제 -> 이력 추적`까지 일관되게 처리할 수 있게 만드는 것이다.

이 기획은 기존의 `사용자 간 차단`과는 목적이 다르다.

- 사용자 간 차단: 조회자 개인의 화면에서 특정 사용자를 숨기는 기능
- 관리자 제재: 운영자가 계정 자체의 활동을 제한하는 기능

---

## 1. 왜 필요한가

현재 프로젝트는 UGC 성격이 있는 서비스다.

- 오픈매트
- 대회
- 신고
- 사용자 간 차단

이 구조에서는 악성 사용자를 단순히 `신고 처리`만으로 대응하기 어렵다. 운영자가 명시적으로 계정 제재를 걸 수 있어야 한다.

스토어 심사 관점에서도 `report + block + moderation` 조합이 중요하다. 현재는 사용자 간 차단과 신고 운영은 있지만, 관리자 제재는 별도 계정 상태로 정리되어 있지 않다.

---

## 2. 현재 프로젝트 기준 상태

### 2.1 이미 있는 것

- `POST /api/v1/users/{id}/block`
- `DELETE /api/v1/users/{id}/block`
- `GET /api/v1/users/blocks`
- `GET /api/v1/admin/reports`
- `PATCH /api/v1/admin/reports/{id}/status`
- `GET /api/v1/admin/open-mats/{id}/report-block`
- 관리자 권한 판별: `admin.user-ids` + `ROLE_ADMIN`
- 사용자 탈퇴 상태: `isWithdrawn`, `withdrawalPending`, `withdrawalScheduledAt`

### 2.2 비어 있는 것

- 관리자용 사용자 목록
- 관리자용 사용자 상세
- 관리자용 제재 이력 조회
- 일시정지 / 영구정지 / 경고 같은 운영 상태 모델
- 제재 해제 기능
- 제재 사유와 처리자 기록

### 2.3 결론

지금은 `사용자 차단`과 `신고 운영`은 있으나, `운영자가 계정을 제어하는 수단`은 없다.

따라서 새 기능은 기존 기능을 대체하는 것이 아니라, **운영 도메인으로 보강**하는 형태가 맞다.

---

## 3. 제품 목표

### 3.1 목표

운영자가 문제 사용자를 빠르게 검색하고, 일시적 또는 영구적으로 계정 활동을 제한할 수 있게 한다.

### 3.2 성공 기준

- 관리자가 특정 사용자를 찾을 수 있다
- 관리자가 제재 사유를 남길 수 있다
- 관리자가 일시정지와 영구정지를 구분해 적용할 수 있다
- 관리자가 제재를 해제할 수 있다
- 제재 이력이 남아 운영 판단의 근거가 된다

---

## 4. 범위 정의

### 4.1 지금 포함할 것

- 관리자 사용자 목록
- 관리자 사용자 상세
- 관리자 제재 생성
- 관리자 제재 해제
- 관리자 제재 이력 조회
- 사용자 상태 노출

### 4.2 지금 제외할 것

- 자동 누적 제재
- 벌점 시스템
- 이의제기 프로세스
- 대량 일괄 제재
- 복합 권한 체계

### 4.3 왜 이렇게 자르는가

심사와 운영의 최소 요건은 `누가`, `왜`, `얼마나`, `언제까지`를 남기고 실제로 계정을 제어할 수 있는지다.  
자동화나 벌점 시스템은 그 다음 단계다.

---

## 5. 권장 용어

용어는 다음처럼 고정하는 것이 좋다.

- `사용자 차단`: 일반 사용자가 다른 사용자를 숨김
- `사용자 제재`: 관리자가 계정 활동을 제한
- `일시정지`: 기간이 있는 제재
- `영구정지`: 해제 전까지 지속되는 제재
- `경고`: 즉시 차단은 아니지만 운영 기록으로 남기는 조치

`탈퇴`는 별도 개념으로 유지한다.

- 탈퇴는 사용자가 계정을 스스로 종료하는 것
- 제재는 운영자가 계정 활동을 제한하는 것

이 둘을 같은 상태로 취급하면 운영과 개인정보 정책이 꼬일 가능성이 높다.

---

## 6. 권장 사용자 상태 모델

관리자 제재를 구현하려면 `User` 엔티티의 탈퇴 상태와 별개로 계정 상태를 둬야 한다.

### 6.1 상태 예시

- `ACTIVE`
- `WARNING`
- `SUSPENDED`
- `BANNED`
- `WITHDRAWN`

### 6.2 상태 의미

- `ACTIVE`: 정상 사용 가능
- `WARNING`: 운영 기록상 경고 상태
- `SUSPENDED`: 기간 내 활동 제한
- `BANNED`: 영구 정지
- `WITHDRAWN`: 사용자가 탈퇴한 상태

### 6.3 권장 원칙

- 탈퇴와 정지를 같은 필드로 처리하지 않는다
- 제재는 이력 테이블로 남긴다
- 현재 상태는 사용자 조회 시 바로 확인 가능해야 한다

---

## 7. 권장 데이터 모델

### 7.1 `user_sanctions`

관리자 제재 이력을 저장하는 **별도 테이블**을 둔다.

필드 예시:

- `id`
- `user_id`
- `type` (`WARNING`, `TEMP_SUSPEND`, `PERMANENT_BAN`, `RELEASE`)
- `reason`
- `memo`
- `starts_at`
- `ends_at`
- `created_by`
- `created_at`
- `released_by`
- `released_at`

### 7.2 `users`

`users`에는 기본 계정 정보만 유지하고, 현재 제재 상태를 빠르게 보여줘야 할 때만 보조 필드를 둔다.

예시:

- `accountStatus`
- `suspensionUntil`
- `sanctionReasonSummary`

### 7.3 분리 이유

이력과 현재 상태를 분리해야 한다.

- 현재 상태만 있으면 운영 근거가 사라진다
- 이력만 있으면 로그인 차단 같은 즉시 판단이 어려워진다
- `user_sanctions`는 감사 추적의 원본이 된다
- `users`의 상태 필드는 조회 편의를 위한 캐시 역할로만 쓴다

---

## 8. 운영 정책

### 8.0 판정 원칙

관리자 제재는 감정적 판단이 아니라 같은 기준으로 반복 가능해야 한다.

기본 판단 축은 아래 5개다.

- `심각도`: 위반 자체가 얼마나 위험한가
- `반복성`: 같은 유형의 위반이 반복되었는가
- `고의성`: 실수인지, 의도적인 위반인지
- `피해 규모`: 노출 범위와 영향이 얼마나 큰가
- `즉시 위험`: 지금 당장 다른 사용자나 서비스에 피해를 주는가

판단 순서는 다음이 좋다.

1. 즉시 위험이 있으면 우선 제재
2. 심각도가 높으면 경고를 생략할 수 있음
3. 경미 위반이라도 반복되면 일시정지로 승격
4. 해제 여부는 재발 방지 가능성과 반성 여부를 함께 본다

### 8.1 경고

- 첫 경미 위반에 사용한다
- 서비스 중단은 하지 않는다
- 제재 이력과 경고 메모만 남긴다

권장 사례:

- 경미한 욕설 또는 비매너 표현 1회
- 실수성 규정 위반
- 금지된 형식이지만 악의성이 낮고 피해가 작음

경고로 충분한 조건:

- 피해 범위가 작다
- 수정 또는 삭제로 회복 가능하다
- 재발 가능성은 있으나 아직 반복 위반은 아니다

### 8.2 일시정지

- 일정 기간 동안 계정 활동을 제한한다
- 권장 방식은 `로그인 허용 + 제한 모드`다
- 사용자는 로그인은 가능하지만 주 서비스는 이용하지 못한다
- 기간은 1일, 3일, 7일, 30일 같은 단위로 운영하는 것이 좋다

권장 허용 범위:

- 마이페이지 조회
- 정지 사유 확인
- 문의 작성
- 이의제기 작성
- 로그아웃

권장 차단 범위:

- 오픈매트 생성 / 수정 / 참가
- 대회 생성 / 수정
- 신고 생성
- 댓글, 채팅, 기타 상호작용 기능
- 서비스 핵심 목록 / 상세 조작

권장 사례:

- 경고 이후 동일 유형 위반 재발
- 반복적인 욕설, 도배, 스팸, 매너 위반
- 특정 사용자에게 지속적인 괴롭힘이나 집요한 추적
- 단일 사건이지만 즉시 영구정지까지는 아니고, 냉각 기간이 필요한 경우
- 자동화된 비정상 활동이 확인되었지만 계정 탈취나 사기까지는 아닌 경우

일시정지가 적합한 조건:

- 반복성이 있다
- 악의성이 어느 정도 보인다
- 즉시 영구정지는 과하나, 계속 활동을 허용하면 피해가 이어질 가능성이 높다

운영 규칙:

- 동일 유형 위반이 2회 이상이면 일시정지 승격을 기본으로 한다
- 서로 다른 경미 위반이 누적되면 더 높은 단계로 올릴 수 있다
- 일시정지는 끝나는 시점을 명확히 둔다

### 8.3 영구정지

- 중대한 위반 또는 재발성 중대 위반에 사용한다
- 관리자 해제 전까지 지속된다
- 기본은 로그인 차단이다
- 필요하면 고객센터 문의 또는 이의제기만 최소 허용할 수 있다

권장 사례:

- 사기, 계정 도용, 금전 유도
- 협박, 명백한 위협, 스토킹성 집착
- 불법 콘텐츠 유통 또는 심각한 법적 리스크가 있는 행위
- 개인정보 유출, 도xxing, 민감정보 공개
- 성적 착취, 아동 관련 유해 콘텐츠
- 제재 회피를 위한 다계정 생성
- 일시정지 이후 동일 유형의 중대 위반 재발

영구정지가 적합한 조건:

- 피해가 크고 회복이 어렵다
- 고의성이 높다
- 즉시 차단하지 않으면 다른 사용자에게 추가 피해가 발생한다
- 서비스 안전성 또는 법적 리스크를 직접 훼손한다

### 8.4 해제

- 해제는 운영자가 수동으로 수행한다
- 해제 사유와 처리자를 남긴다

해제 판단 기준:

- 경미 위반의 경우 재발 방지 조치가 확인됨
- 일시정지 기간이 만료됨
- 신고 내용이 오인 또는 무효로 정리됨
- 본인 인증 또는 운영 확인으로 계정 안전성이 회복됨

영구정지 해제는 예외적으로만 허용한다.

### 8.5 정지 시 접근 정책

정지 상태는 UI가 아니라 서버 정책으로 강제해야 한다.

권장 원칙:

- `WARNING`: 정상 사용 가능
- `TEMP_SUSPEND`: 로그인 가능, 제한 모드만 허용
- `PERMANENT_BAN`: 기본적으로 로그인 차단

제한 모드에서 허용할 API는 최소화한다.

- `GET /api/v1/users/me`
- `GET /api/v1/users/me/settings`
- `GET /api/v1/inquiries`
- `POST /api/v1/inquiries`
- `GET /api/v1/inquiries/{id}`
- `GET /api/v1/users/blocks`
- `POST /api/v1/users/{id}/block`
- `DELETE /api/v1/users/{id}/block`

서비스 정책에 따라 추가 허용 가능한 기능:

- 로그아웃
- 계정 상태 안내
- 제재 이의제기 제출

제한 모드에서 차단할 API는 다음 범주로 본다.

- 오픈매트 작성 / 참가 / 수정
- 대회 작성 / 수정
- 신고 생성
- 다른 사용자와의 상호작용
- `PUT /api/v1/users/me`
- `DELETE /api/v1/auth/withdraw`

정책 권장안:

- `문의하기 작성`: 허용
- `도움말 조회`: 허용
- `알림 on/off`: 허용
- `차단한 사용자 관리`: 허용
- `로그아웃`: 허용
- `사용자 정보 수정`: 기본 차단
- `탈퇴하기`: 기본 차단

영구정지 사용자에게도 문의 또는 이의제기 경로를 열지 여부는 별도 운영 정책으로 확정한다.

필요 항목:

- 가입일

- 최근 제재 시각

필요 기능:

### 9.2 관리자 사용자 상세

필요 항목:

- 프로필 기본 정보
- 계정 상태
- 신고 누적
- 최근 활동
- 제재 이력

필요 기능:

- 경고
- 일시정지
- 영구정지

### 9.3 신고 상세와의 관계

현재 신고 운영 화면은 `검토` 중심으로 유지하는 것이 좋다.

- 신고 상세에서 직접 제재를 실행하는 UI는 오조작 위험이 있다
- 대신 사용자 상세로 이동하는 링크만 제공하는 구성이 안전하다

## 10. API 기획

### 10.1 관리자 사용자 조회

- `GET /api/v1/admin/users`
- `GET /api/v1/admin/users/{id}`

### 10.2 제재 이력

- `GET /api/v1/admin/users/{id}/sanctions`

### 10.3 제재 생성

- `POST /api/v1/admin/users/{id}/sanctions`

요청 예시:

```json
{
  "type": "TEMP_SUSPEND",
  "reason": "욕설 및 반복 신고",
  "memo": "커뮤니티 규정 위반",
  "endsAt": "2026-04-20T00:00:00"
}
```

### 10.4 제재 해제

- `DELETE /api/v1/admin/users/{id}/sanctions/{sanctionId}`

또는 별도 해제 API를 둬도 된다.

권장 방식은 제재 이력을 유지한 채 상태만 해제하는 것이다.

### 10.5 공통 규칙

- 모든 관리자 API는 `ROLE_ADMIN`만 허용
- `admin.user-ids` 기준으로 관리자 판별
- 제재 생성과 해제는 감사 로그가 남아야 한다

## 11. 백엔드 동작 원칙

### 11.1 로그인 차단 여부

일시정지와 영구정지에서 로그인 자체를 막을지 먼저 정해야 한다.

권장안:

- `WARNING`: 로그인 가능
- `TEMP_SUSPEND`: 로그인 불가 또는 제한 로그인
- `PERMANENT_BAN`: 로그인 불가

### 11.2 작성 제한 여부

정지 상태에서는 다음을 제한하는 쪽이 일관적이다.

- 오픈매트 작성
- 대회 작성
- 문의 생성
- 신고 생성

제한 범위는 서비스 정책에 따라 좁히거나 넓힐 수 있다.

### 11.3 조회 제한 여부

조회 제한은 신중해야 한다.

- 일반적으로는 `작성/로그인 제한`이 우선
- 공개 목록 노출까지 막을지는 운영 정책으로 별도 결정

## 12. 기존 코드와의 연결 포인트

### 12.1 사용자 도메인

현재 `User` 엔티티에는 다음이 있다.

- `isWithdrawn`
- `withdrawalPending`
- `withdrawalScheduledAt`
- `blockedUserLinks`

제재는 이 필드들과 목적이 다르므로, 새 필드를 추가하거나 별도 엔티티로 분리하는 편이 맞다.

### 12.2 인증

현재 관리자 권한은 `admin.user-ids`와 JWT 기반 `ROLE_ADMIN`으로 판별한다.  
새 관리자 API는 이 정책을 그대로 따라야 한다.

### 12.3 신고 운영

현재 신고 운영은 `ReportService`와 `/api/v1/admin/reports`로 분리되어 있다.  
제재는 신고 처리의 후속 조치로 연결되지만, 신고 API에 억지로 섞지 않는 것이 좋다.

### 12.4 사용자 차단과의 관계

사용자 차단은 이미 구현된 개인 필터다.

- 차단은 조회자 기준
- 제재는 운영자 기준

둘은 함께 존재해야 하지만, 저장 방식과 UX는 분리한다.

## 15. 리스크

### 15.1 탈퇴와 제재 혼동

`isWithdrawn`을 제재 수단으로 재사용하면 운영이 꼬인다.  
반드시 별도 상태로 관리해야 한다.

### 15.2 오조작 위험

신고 상세 화면에서 바로 제재를 걸 수 있으면 실수 가능성이 높다.  
사용자 상세에서만 실행하도록 제한하는 편이 낫다.

### 15.3 정책 부재

상태만 만들고 기준이 없으면 운영 일관성이 무너진다.  
최소한 `일시정지`, `영구정지`, `해제`의 적용 기준은 문서로 남겨야 한다.
