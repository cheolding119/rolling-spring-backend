0. 브랜치 운영 규칙
   작업 내용에 따라 새로운 브랜치를 생성한 뒤 작업을 진행합니다.
커밋제목 내용 모두 한글로 작성한다. 커밋 내용은 구체적으로 작성한다 

기능 추가, 버그 수정, 리팩토링, 문서 수정 등 작업 단위가 달라지면 기존 브랜치를 재사용하지 않고 목적에 맞는 새 브랜치를 생성합니다.

모든 커밋은 해당 작업 브랜치에서 작성하며, 작업 완료 후 원격 저장소에 push 합니다.

불필요한 테스트는 진행하지 않는다 .

브랜치 명 앞에는 codex 를 붙이지 않는다 
브랜치 이름은 작업 내용을 식별할 수 있도록 작성합니다. 예시: feature/auth-login, fix/payment-timeout, docs/commit-convention


1. 기본 구조 (Basic Structure)
   커밋 메시지는 다음 구조를 엄격하게 따릅니다.
<타입>(<적용 범위>): <제목>

- <변경 내용 1>
- <변경 내용 2>

[꼬리말]

💡 작성 예시
feat(openmat): 오픈매트 생성 및 취소 기능 구현

- 오픈매트 생성 API 연동 및 UI 구현
- 정원 초과 시 신청 취소 버튼 비활성화 로직 추가

Fixes: #45


2. 타입 (Type)
   커밋의 성격을 한눈에 파악할 수 있도록 소문자로 작성합니다. 다음 중 하나를 선택하여 사용합니다.

feat: 새로운 기능 추가

fix: 버그 수정

docs: 문서 수정 (README.md, 주석 등)

style: 코드 포맷팅, 세미콜론 누락 등 코드의 로직 변경이 없는 경우

refactor: 코드 리팩토링 (기능 변경 없이 코드 구조 개선)

test: 테스트 코드 추가, 리팩토링 테스트 코드 추가

chore: 빌드 업무 수정, 패키지 매니저 설정 변경, 기타 설정 변경

perf: 성능 개선

ci: CI/CD 설정 파일 및 스크립트 변경

3. 적용 범위 (Scope) - 필수
   변경이 일어난 도메인이나 모듈을 소괄호 () 안에 소문자로 명시합니다. 이를 통해 어느 도메인에서 발생한 작업인지 명확히 합니다.

예시: feat(auth), fix(ui), feat(openmat), refactor(tournament)

4. 제목 (Subject) 작성 규칙
   포맷: <타입>(<적용 범위>): <제목> (콜론 뒤에 띄어쓰기 1칸 필수)

명령문/명사형으로 간결하게 작성합니다. (예: "수정했습니다" (X) -> "수정" (O))

제목의 끝에는 마침표(.)를 붙이지 않습니다.

무엇을 했는지보다 왜 했는지, 어떤 결과를 낳았는지에 초점을 맞추어 작성합니다. (50자 이내 권장)

5. 본문 (Body) 작성 규칙
   제목 아래에 한 줄을 띄우고 작성합니다.

하이픈(-)을 사용한 불릿 포인트 형식으로 작성하여 가독성을 높입니다.

변경의 이유(Why)와 어떻게 변경했는지(How)를 구체적으로 나열합니다.

- 기존 로그인 API 타임아웃 3초에서 5초로 연장
- 카카오 소셜 로그인 실패 시 보여줄 에러 팝업 UI 추가

# 아직 안정해짐
6. 꼬리말 (Footer) 작성 규칙 - 선택
   본문 아래에 한 줄을 띄우고 작성합니다.

관련된 이슈 트래커(Jira, Github Issues 등)의 번호를 적어 커밋과 이슈를 연결합니다.

예시: Fixes: #123, Resolves: #456, Related to: #789

7. 브랜치 운영 규칙 - 추가
   작업은 항상 `Dev` 브랜치를 기준으로 진행합니다.

- 먼저 `Dev` 브랜치를 생성합니다.
- 이후 실제 기능/버그 작업은 `Dev`에서 분기한 작업 브랜치에서 진행합니다.
- 작업이 완료되면 작업 브랜치를 `Dev`에 머지하고, `Dev` 브랜치를 원격에 커밋 푸시합니다.
- 모든 변경이 `Dev`에 반영된 뒤 `Dev` 브랜치를 `Main` 브랜치에 머지합니다.
