# 훈련일지 댓글 신고/차단 확장 기획안

## 1. 문서 목적

- 훈련일지 상세의 댓글 기능이 iPhone, Google 심사 기준에서 더 안전하게 운영되도록 `신고`, `차단`, `운영 처리` 기준을 정리한다.
- 현재 프로젝트에 이미 있는 `사용자 차단`, `댓글 신고`, `관리자 제재` 체계를 최대한 재사용하는 방향으로 범위를 정의한다.

## 2. 현재 프로젝트 기준 확인 결과

### 2.1 이미 있는 기능

#### 사용자 차단

- `POST /api/v1/users/{id}/block`
- `DELETE /api/v1/users/{id}/block`
- `GET /api/v1/users/blocks`

현재 정책:

- 차단은 `사용자 대 사용자` 기준이다.
- 오픈매트, 대회, 친구 기능에서 차단 관계를 이미 검사하고 있다.
- source of truth: [common-models.md](C:/rolling/rolling-spring-backend/rolling-api/docs/domain_and_spec/shared/common-models.md:126)

#### 공용 신고 서비스

- `report` 도메인에 `ReportService`, `ReportReason`, `ReportStatus`, `ReportTargetType`가 존재한다.
- 세미나, 오픈매트, 대회는 이미 공용 신고 서비스 패턴을 사용한다.
- 신고 공통 정책:
  - 자기 자신 신고 불가
  - 동일 사용자 중복 신고 불가
  - 신고 사유 필수

#### 커뮤니티 댓글 신고

- 커뮤니티는 댓글 신고 API가 이미 존재한다.
- `POST /api/v1/community/comments/{commentId}/report`
- 커뮤니티 댓글은 전용 엔티티, 전용 저장소, 전용 관리자 조회/처리 흐름으로 운영 중이다.
- 즉, 현재 프로젝트에서 `댓글 신고`의 source of truth는 공용 `report` 확장이 아니라 `전용 댓글 신고 모델 패턴`에 가깝다.
- source of truth: [community.md](C:/rolling/rolling-spring-backend/rolling-api/docs/domain_and_spec/community.md:1)

#### 관리자 제재 체계

- `user_sanctions` 이력과 `users.accountStatus` 캐시 기반 제재 체계가 이미 있다.
- 신고 누적 후 최종 조치는 별도 신규 시스템이 아니라 기존 관리자 제재 체계로 연결하는 것이 맞다.

### 2.2 현재 훈련일지 댓글의 상태

- 훈련일지 댓글/대댓글 생성, 수정, 삭제는 이미 구현되어 있다.
- 친구 관계/친구 공개 설정/차단 관계에 따라 접근 제어가 이미 일부 들어가 있다.
- 하지만 아래는 아직 없다.
- 훈련일지 댓글 신고 API
- 훈련일지 댓글 신고 관리자 조회/처리 모델
- 차단 관계 댓글 목록 필터 정책
- 신고 누적 자동 삭제 정책

즉, 현재 훈련일지 댓글은 `작성 기능`은 있으나 `moderation 기능`이 완성되지 않은 상태다.

## 3. 왜 지금 필요한가

훈련일지 댓글은 사용자 생성 콘텐츠다.

스토어 심사 관점에서 댓글 기능이 있으면 보통 아래를 요구한다.

1. 부적절한 댓글을 신고할 수 있어야 함
2. 특정 사용자를 차단할 수 있어야 함
3. 운영자가 신고를 확인하고 조치할 수 있어야 함

현재 프로젝트는 이 3가지 기반이 이미 일부 존재하므로, 훈련일지 댓글도 같은 기준으로 편입하는 것이 가장 자연스럽다.

## 4. 제품 방향

핵심 원칙:

- 훈련일지 댓글에만 별도 moderation 철학을 만들지 않는다.
- 기존 `사용자 차단`, `댓글 신고 패턴`, `관리자 제재` 체계를 재사용한다.
- 새로 만드는 것은 `훈련일지 댓글`을 그 체계에 연결하는 최소 도메인/API/UI다.

## 5. 차단 기능 방향

### 5.1 사용자 행동

훈련일지 댓글/대댓글 작성자 프로필 액션에서:

- `사용자 차단`
- `신고`

진입이 가능해야 한다.

### 5.2 차단 후 동작

권장 정책:

1. 내가 차단한 사용자의 훈련일지 댓글은 상세 화면에서 숨김
2. 나를 차단한 사용자의 훈련일지 댓글도 숨김
3. 차단 관계에서는 해당 사용자와 추가 댓글/대댓글 상호작용 불가

MVP 권장 표시 방식:

- 댓글 row 자체를 완전히 제거
- 차단 대상 원댓글이 제거되면 그 하위 대댓글도 함께 제거
- 댓글 수는 화면에 실제 노출되는 댓글 기준으로 맞춘다

이유:

- 원댓글만 제거하고 대댓글을 남기면 트리 구조가 깨진다.
- 화면에 보이는 댓글 수와 상단 count가 다르면 UX 혼란이 생긴다.

### 5.3 백엔드 관점 구현 방향

- 댓글 목록 조회 시 `viewerUserId` 기준 차단 관계 댓글 제외
- 차단 대상 원댓글이 제외되면 해당 원댓글의 대댓글도 함께 제외
- 댓글 작성 시
  - 댓글 대상 기록 작성자와 차단 관계면 금지
  - 대댓글 대상 댓글 작성자와 차단 관계면 금지

## 6. 신고 기능 방향

### 6.1 사용자 행동

훈련일지 댓글/대댓글마다 `신고하기` 진입이 가능해야 한다.

### 6.2 신고 방식

현재 프로젝트 기준으로는 `커뮤니티 댓글 신고 패턴`을 따르는 쪽이 가장 자연스럽다.

권장 API:

- `POST /api/v1/training-logs/comments/{commentId}/report`

Request body:

- `reason`
- `customReason`

신고 정책:

- 자기 댓글 신고 불가
- 동일 사용자의 동일 댓글 중복 신고 불가
- `OTHER`일 때 `customReason` 필수
- 댓글 또는 대댓글이 신고 3회 이상 누적되면 자동으로 soft delete 처리한다.
- 원댓글이 신고 누적으로 자동 삭제되면 그 하위 대댓글도 함께 soft delete 처리한다.

### 6.3 운영 처리 방향

가장 권장하는 방향은 `커뮤니티 댓글과 같은 전용 댓글 신고 모델`을 따르는 것이다.

즉:

- `TrainingLogCommentReport` 전용 엔티티 추가
- `TrainingLogCommentReportRepository` 전용 저장소 추가
- 관리자 조회/처리도 전용 댓글 신고 응답 모델로 연결
- 신고 사유 enum과 처리 상태는 기존 공용 값을 재사용할 수 있다.

이 방향의 장점:

- 현재 프로젝트의 `댓글 신고` 구조와 일관된다.
- 커뮤니티 댓글 신고와 같은 운영 흐름으로 맞출 수 있다.
- 훈련일지 댓글의 자동 삭제, 대댓글 연쇄 삭제 같은 댓글 전용 규칙을 넣기 쉽다.

## 7. 관리자 처리 방향

### 7.1 최소 범위

관리자는 훈련일지 댓글 신고를 조회하고 상태를 변경할 수 있어야 한다.

권장 방식:

- 커뮤니티 댓글 신고 관리자 화면과 같은 전용 댓글 신고 흐름으로 확장

즉 신규 공용 신고 타입 확장보다 아래가 더 낫다.

- `훈련일지 댓글 신고 전용 관리자 목록/상세/상태 변경` 흐름 추가

### 7.2 최종 조치

관리자 최종 조치 예시:

- 무조치
- 댓글 삭제
- 사용자 경고
- 사용자 일시 정지

여기서 사용자 제재는 기존 `user_sanctions` 흐름으로 처리한다.

## 8. 권장 API 초안

### 8.1 댓글 신고

`POST /api/v1/training-logs/comments/{commentId}/report`

- 인증: 필요
- Response data: `null`

Request body:

| 필드 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `reason` | `ReportReason` | O | 신고 사유 |
| `customReason` | `String?` | - | 기타 사유 |

에러:

- `NOT_FOUND`
- `SELF_REPORT_NOT_ALLOWED`
- `ALREADY_REPORTED`
- `VALIDATION_ERROR`
- `FORBIDDEN`

### 8.2 기존 차단 API 재사용

- `POST /api/v1/users/{id}/block`
- `DELETE /api/v1/users/{id}/block`

훈련일지 댓글에서는 별도 차단 API를 만들지 않고 현재 사용자 차단 API를 재사용한다.

## 9. 상세 정책 제안

### 9.1 본인 기록의 댓글에서도 동일 정책 적용

현재 본인 훈련일지에도 댓글 작성이 가능하므로 moderation 정책도 동일해야 한다.

즉:

- 본인 훈련일지 댓글도 신고 가능
- 본인 훈련일지 댓글 작성자도 차단 가능
- 훈련일지 주인은 자신의 기록에 달린 `본인 댓글`과 `다른 사람 댓글`을 모두 삭제할 수 있다.

### 9.2 삭제된 댓글과 신고

권장 정책:

- 이미 삭제된 댓글은 새 신고 불가
- 기존 신고 이력은 유지
- 원댓글이 신고 누적으로 삭제되면 연결된 대댓글도 함께 soft delete 처리한다.

### 9.3 대댓글과 차단

권장 정책:

- 차단 관계인 사용자의 원댓글에는 대댓글 작성 불가
- 차단 관계인 사용자의 대댓글에도 추가 상호작용 불가
- 차단 대상 원댓글이 화면에서 제거되면 그 하위 대댓글도 함께 제거한다.

### 9.4 알림과 차단

차단 관계가 생기면:

- 이후 해당 사용자 간 댓글 알림 발행 금지

이 항목은 현재 댓글 알림 시스템과 함께 검토가 필요하다.

## 10. 구현 권장 순서

### Phase 1. 도메인/정책 확정

- 전용 `TrainingLogCommentReport` 모델 구조 확정
- 차단 시 댓글 목록 필터 정책 확정
- 차단 시 작성 제한 정책 확정
- 신고 3회 자동 삭제 정책 확정
- 원댓글 삭제 시 대댓글 연쇄 삭제 정책 확정

### Phase 2. 신고 기능 구현

- 훈련일지 댓글 신고 API 추가
- 전용 댓글 신고 엔티티/저장소/서비스 연결
- 신고 3회 누적 시 soft delete 처리 구현

### Phase 3. 차단 필터 구현

- 댓글 목록 조회 시 차단 사용자 댓글 제외
- 댓글 작성/대댓글 작성 시 차단 관계 검사
- 차단 대상 원댓글의 대댓글 일괄 제거 처리

### Phase 4. 관리자 연동

- 관리자 훈련일지 댓글 신고 목록/상세/상태 변경 연결
- 훈련일지 주인의 댓글 삭제 권한과 관리자 처리 정책 정리

### Phase 5. 테스트와 문서 동기화

- 신고 중복/자기 신고/삭제 댓글 신고/차단 관계 회귀 테스트
- 신고 3회 자동 삭제와 원댓글 삭제 시 대댓글 연쇄 삭제 테스트
- domain_and_spec 문서 동기화

## 11. 권장 결론

훈련일지 댓글 moderation은 아래 방식이 가장 적절하다.

1. 차단은 기존 사용자 차단 API 재사용
2. 신고는 커뮤니티 댓글과 같은 전용 댓글 신고 모델 패턴 사용
3. 관리자 조치는 기존 제재 체계 재사용
4. 새로 만드는 것은 `훈련일지 댓글을 기존 체계에 연결하는 최소 API와 필터`

즉, `신고/차단 시스템을 새로 만드는 것`이 아니라
`훈련일지 댓글을 기존 신고/차단/제재 시스템에 편입시키는 작업`으로 정의하는 것이 맞다.

### Phase 2. 훈련일지 댓글 신고 API 및 전용 댓글 신고 모델 연동

- [x] DB 스키마 변경안 작성 (`training_log_comment_reports` 테이블, unique 제약, 조회 인덱스, 필요 시 comment report count 반영 방식)
