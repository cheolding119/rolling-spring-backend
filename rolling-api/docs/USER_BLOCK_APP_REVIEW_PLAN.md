# 사용자 차단 기능 기획서

이 문서는 `오픈매트`와 `대회` 같은 사용자 생성 콘텐츠(UGC, 사용자 생성 콘텐츠) 환경에서, 사용자가 특정 사용자를 차단해서 그 사람의 콘텐츠를 보지 않도록 만드는 기능을 기획한 문서다.

목표는 단순한 내부 구현이 아니라, iOS App Review(앱스토어 심사)와 Google Play Console(구글 플레이 콘솔 심사)에서 요구하는 `report + block + moderation`(신고 + 차단 + 운영 검수) 구조에 맞게 기능을 완성하는 것이다.

---

## 1. 심사 기준

### 1.1 Apple App Store

Apple은 UGC(사용자 생성 콘텐츠) 또는 소셜 기능이 있는 앱에 대해 아래를 요구한다.

- 불쾌하거나 문제 있는 콘텐츠를 필터링할 방법
- offensive content(유해/불쾌한 콘텐츠)를 신고할 수 있는 메커니즘
- abusive user(문제 사용자)를 차단할 수 있는 기능
- 사용자에게 쉽게 닿을 수 있는 공개된 연락처 정보

공식 문서:
- [Apple App Store Review Guidelines - 1.2 User-Generated Content](https://developer.apple.com/app-store/review/guidelines)

### 1.2 Google Play Console

Google Play는 UGC(사용자 생성 콘텐츠) 앱에 대해 다음을 요구한다.

- 명확한 Terms of Use(이용약관) / user policy(사용자 정책)
- objectionable content(문제성 콘텐츠) 정의
- in-app reporting and blocking(앱 내 신고 및 차단) 기능
- 사용자와 콘텐츠에 대한 조치
- 공개 UGC 앱이면 사용자와 콘텐츠를 모두 report/block 할 수 있어야 함

공식 문서:
- [Google Play - User Generated Content](https://support.google.com/googleplay/android-developer/answer/9876937?hl=en)
- [Google Play - Understanding moderation requirements](https://support.google.com/googleplay/android-developer/answer/12923286?hl=en)

### 1.3 이 서비스에 적용되는 의미

현재 서비스는 사용자가 오픈매트와 대회 콘텐츠를 생성하는 구조다. 따라서 차단 기능은 단순 편의 기능이 아니라, 심사 대응용 필수 안전장치로 봐야 한다.

---

## 2. 현재 상태

현재 코드에는 사용자 차단 API와 관계 저장은 있다.

- `POST /api/v1/users/{id}/block`
- `DELETE /api/v1/users/{id}/block`
- `user_blocked_users` 조인 테이블

하지만 현재 확인된 코드 범위에서는 아래가 아직 완성되어 있지 않다.

- 차단한 사용자의 오픈매트 / 대회 목록을 자동으로 숨기는 필터
- 차단한 사용자의 상세 화면 접근 정책
- 차단 목록 조회 API
- 차단 해제 화면
- 차단이 알림/추천/검색에 미치는 범위 정의

즉, 지금 구현은 `관계 저장`까지만 되어 있고, `사용자 체감 기능`으로는 부족하다.

---

## 3. 기능 정의

### 3.1 이름

사용자 차단

### 3.2 목적

내가 원치 않는 사용자의 콘텐츠를 보지 않도록 막는다.

### 3.3 차단이 의미하는 것

차단은 `신고`와 다르다.

- 신고는 운영자에게 문제 콘텐츠를 알리는 기능이다.
- 차단은 내 화면에서 특정 사용자를 제거하는 기능이다.

차단은 개인화된 필터이며, 운영 제재가 아니다.

---

## 4. 제품 원칙

### 4.1 차단은 즉시 반영되어야 한다

차단 버튼을 누르면, 새로고침 후 바로 목록에서 사라져야 한다.

### 4.2 차단은 되돌릴 수 있어야 한다

차단은 영구 제재가 아니라 사용자 제어 기능이다. 언제든 해제할 수 있어야 한다.

### 4.3 차단과 신고는 분리한다

같은 메뉴 안에 둘 수는 있지만, 의미는 분명히 달라야 한다.

- 차단: 내가 안 보고 싶어서 숨김
- 신고: 운영에 문제를 알림

### 4.4 차단된 사용자는 내 설정을 알 필요가 없다

차단은 보통 비공개 사용자 제어다. 차단한 상대방에게 별도 알림을 보내지 않는다.

---

## 5. 사용 시나리오

### 5.1 오픈매트에서 차단

사용자가 오픈매트 상세에서 작성자를 차단하면:

- 그 작성자의 다른 오픈매트가 목록에서 보이지 않는다
- 검색 결과에서도 제외된다
- 내 피드/추천/관심 목록에서도 제외된다
- 차단된 작성자의 상세 화면은 차단 안내 화면으로 대체된다

### 5.2 대회에서 차단

사용자가 대회 상세에서 작성자를 차단하면:

- 그 작성자의 다른 대회가 목록에서 보이지 않는다
- 검색 결과에서도 제외된다
- 차단된 작성자의 상세 화면은 차단 안내 화면으로 대체된다

### 5.3 차단 해제

차단 목록에서 해제하면:

- 목록과 검색 결과에 다시 나타날 수 있다
- 이미 차단 해제한 뒤에는 일반 사용자처럼 다시 콘텐츠를 볼 수 있다

---

## 6. 화면 기획

### 6.1 차단 진입점

차단은 사용자가 자연스럽게 찾을 수 있어야 한다.

추천 진입점:

- 오픈매트 상세의 작성자 메뉴
- 대회 상세의 작성자 메뉴
- 사용자 마이페이지 메뉴

### 6.2 차단 목록 화면

마이페이지에 `차단한 사용자` 카드를 두고 선택하면 `차단한 사용자` 의 목록을 둔다.

필수 기능:

- 차단된 사용자 목록 보기
- 차단 해제 버튼

### 6.3 차단 안내 화면

차단된 사용자의 콘텐츠를 열려고 할 때는 다음 중 하나를 보여준다.

- "차단한 사용자의 콘텐츠입니다"
- 차단 해제 버튼
- 뒤로가기 버튼

직접 링크로 들어와도 빈 화면이 아니라, 차단 이유가 명확한 안내를 보여줘야 한다.

---

## 7. 노출 정책

차단 기능은 `viewer-centric`(조회자 기준)으로 동작해야 한다.

즉, 내가 특정 사용자를 차단하면 내 화면에서만 그 사용자의 콘텐츠가 숨겨진다.

### 7.1 숨겨야 하는 곳

- 오픈매트 목록
- 오픈매트 검색 결과
- 오픈매트 상세
- 대회 목록
- 대회 검색 결과
- 대회 상세
- 알림 목록
- 추천 영역

### 7.2 숨기지 않아도 되는 곳

- 관리자 신고 목록
- 운영 로그
- 내부 통계

### 7.3 직접 접근 정책

딥링크나 과거 즐겨찾기로 들어온 경우에도, 차단한 사용자의 콘텐츠는 일반 콘텐츠처럼 보여주지 않는다.

권장 방식:

- `BLOCKED_USER_CONTENT` 같은 명시적 에러
- 또는 차단 안내용 placeholder(대체) 화면

---

## 8. 데이터 설계

### 8.1 현재 데이터

현재는 `User.blockedUserLinks` / `UserBlock` 관계가 이미 있다.

이 구조는 사용자 A가 사용자 B를 차단했다는 정보를 저장하기에 충분하다.

### 8.2 권장 저장 방식

현재 조인 테이블 `user_blocked_users`를 그대로 사용한다.

차단 시각은 `blockedAt`으로 저장한다.

App Review(앱 심사) 대응만 놓고 보면 `updatedAt` 같은 추가 메타데이터는 필수는 아니다.

### 8.3 조회 방법

현재 로그인한 사용자의 차단 대상 ID 목록을 먼저 가져오고, 콘텐츠 조회 쿼리에서 제외한다.

핵심은 아래다.

- 한 번 차단한 사용자의 `hostId` 또는 `authorId`는 feed/search/detail(목록/검색/상세)에서 제외
- 차단 목록은 페이지 단위 조회가 아니라 설정 화면용으로 별도 조회

## 9. API 기획

### 9.1 이미 있는 API

- `POST /api/v1/users/{id}/block`
- `DELETE /api/v1/users/{id}/block`
- `GET /api/v1/users/blocks`

### 9.2 추가 권장 API

- `GET /api/v1/users/blocks/{id}`
  - 차단 여부 단건 확인

### 9.3 응답 정책

차단 관련 API는 idempotent(멱등)하게 동작하는 것이 좋다.

- 이미 차단된 사용자를 다시 차단해도 성공 응답
- 차단되지 않은 사용자를 다시 차단 해제해도 성공 응답

이 방식이 앱에서 가장 다루기 쉽다.

---

## 10. 신고와의 관계

차단과 신고는 함께 있어야 한다.

### 차단

- 내 화면에서 보기 싫은 사용자를 숨긴다
- 개인화 기능이다

### 신고

- 운영 정책 위반을 알린다
- 운영자 검토 대상이다

### 둘 다 필요한 이유

- 차단만 있으면 운영적인 대응이 부족하다
- 신고만 있으면 사용자가 즉시 불편한 콘텐츠를 피할 수 없다

Apple과 Google이 요구하는 것도 결국 `report + block + moderation`(신고 + 차단 + 운영 검수)의 조합이다.

---

## 11. App Review(앱 심사) 대응 포인트

심사 통과를 위해서는 아래가 분명해야 한다.

- 차단 버튼이 앱 안에서 바로 보인다
- 차단 해제가 앱 안에서 가능하다
- 차단한 사용자의 콘텐츠가 실제로 숨겨진다
- 차단이 단순한 서버 저장이 아니라 UI(화면)에 반영된다
- 신고 기능과 차단 기능이 분리되어 있다
- 고객지원 연락처가 앱 안과 스토어 메타데이터에서 확인 가능하다
- Terms of Use(이용약관) / user policy(사용자 정책)가 콘텐츠 생성 전에 노출된다

---

## 12. 구현 완료 기준

아래를 만족하면 기능이 완료된 것으로 본다.

1. 사용자가 다른 사용자를 차단할 수 있다.
2. 차단한 사용자의 오픈매트와 대회가 목록에서 보이지 않는다.
3. 검색 결과에서도 차단한 사용자의 콘텐츠가 제외된다.
4. 차단된 사용자의 상세 화면은 일반 콘텐츠처럼 보이지 않는다.
5. 차단 목록을 보고 해제할 수 있다.
6. 차단과 신고가 분리되어 있다.
7. 차단한 사용자에게 별도 알림이 가지 않는다.

---

## 13. 현재 구현 기준의 평가

현재 백엔드는 `차단 관계 저장`은 되어 있지만, `차단 체감 경험`은 아직 완성되지 않았다.

심사 대응 관점에서는 다음이 부족하다.

- 차단한 사용자 콘텐츠를 숨기는 목록 필터
- 차단 목록 화면
- 직접 접근 시 차단 안내
- 노출 범위 정의

따라서 지금 상태는 `기능 존재` 수준이지, `심사 대응 완료` 수준은 아니다.
