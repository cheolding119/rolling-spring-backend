프로젝트 협업을 위한 Git 커밋 컨벤션 가이드
이 문서는 우리 팀이 소스 코드를 관리하고 협업할 때 지켜야 할 Git 커밋 메시지 작성 규칙을 정의합니다. 명확하고 일관된 커밋 메시지는 코드의 변경 이력을 파악하기 쉽게 만들고, 버그 추적 및 협업 효율을 높이는 데 중요한 역할을 합니다.
커밋은 한글로 작성 해야함 

1. 기본 구조 (Basic Structure)
   커밋 메시지는 크게 세 부분으로 구성됩니다.

<타입>[적용 범위]: <제목>

[본문]

[꼬리말]
제목(Subject): (필수) 커밋의 목적을 간략히 설명합니다. (50자 이내 권장)

본문(Body): (선택) 변경한 이유와 상세 내용을 설명합니다. (72자마다 줄바꿈 권장)

꼬리말(Footer): (선택) 관련된 이슈 트래커(Jira, Github Issues 등)의 ID를 작성할 때 사용합니다.

2. 타입 (Type)
   커밋의 성격을 한눈에 파악할 수 있도록 가장 중요한 역할을 합니다. 다음 중 하나를 선택하여 사용합니다.

Feat: 새로운 기능 추가

Fix: 버그 수정

Docs: 문서 수정 (README.md, 주석 등)

Style: 코드 포맷팅, 세미콜론 누락 등 코드의 로직 변경이 없는 경우

Refactor: 코드 리팩토링 (기능 변경 없이 코드 구조 개선)

Test: 테스트 코드 추가, 리팩토링 테스트 코드 추가

Chore: 빌드 업무 수정, 패키지 매니저 설정 변경, 기타 설정 변경

Perf: 성능 개선

Ci: CI 설정 파일 및 스크립트 변경

3. 적용 범위 (Scope) - 선택 사항
   변경이 일어난 도메인이나 모듈을 명시합니다. 괄호 [] 안에 소문자로 작성합니다.

예시: Feat[auth]: 로그인 기능 추가, Fix[ui]: 버튼 색상 오류 수정

4. 제목 (Subject) 작성 규칙
   명령문/현재형으로 작성합니다. (예: "Fixed bug" (X) -> "Fix bug" (O) / "추가했습니다" (X) -> "추가" (O))

첫 글자는 소문자로 시작합니다. (영어일 경우)

문장 끝에 마침표(.)를 붙이지 않습니다.

무엇을 했는지보다 왜 했는지에 초점을 맞추어 작성합니다.

5. 본문 (Body) 작성 규칙
   선택 사항이지만, **변경의 이유(Why)**와 **어떻게 변경했는지(How)**를 설명하는 데 유용합니다.

여러 줄로 작성할 수 있습니다.

6. 꼬리말 (Footer) 작성 규칙
   선택 사항입니다.

관련된 이슈 번호를 적습니다.

예시: Fixes: #123, Resolves: #456
