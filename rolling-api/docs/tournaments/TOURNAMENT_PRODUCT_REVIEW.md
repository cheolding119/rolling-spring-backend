# 대회 기능 기획 검토 메모

## 1. 목적

이 문서는 현재 Rolling 앱의 `대회` 기능 기획이 괜찮은 방향인지, 무엇이 아직 덜 정리됐는지 이해하기 쉽게 설명하기 위한 검토 메모다.

기술 구현 자체보다 아래 질문에 답하는 데 초점을 둔다.

- 대회 기능이 지금 서비스 목표에 맞는가
- 지금 열어도 되는 범위와 아직 이른 범위가 무엇인가
- 왜 문서와 정책이 충돌해 보이는가
- 다음 제품 결정은 무엇부터 해야 하는가

## 2. 한 줄 결론

- `대회 탐색 기능` 자체는 서비스 방향과 잘 맞는다.
- 다만 `일반 사용자가 직접 대회를 등록하는 기능`은 아직 이르다.
- 지금은 `큐레이션형 대회 피드`로 운영하고, 사용자 등록은 운영 정책이 갖춰진 뒤 여는 편이 더 안전하다.

## 3. 현재 서비스에서 대회 기능이 맡아야 할 역할

Rolling의 핵심 문제 정의는 `흩어진 정보를 한곳에 모아 사용자가 쉽게 찾게 하는 것`이다.

즉 대회 기능의 1차 역할은 아래에 가깝다.

- 사용자가 대회 정보를 빠르게 찾는다
- 접수 마감 전 대회를 한눈에 비교한다
- 상세를 보고 외부 신청 링크로 이동한다

반대로 현재 문서 일부는 대회를 `사용자 게시판`처럼 열어두는 방향도 섞여 있다.
이 두 방향은 비슷해 보여도 실제 제품 의미는 꽤 다르다.

## 4. 왜 이번 검토에서 이슈가 나왔는가

이번 검토에서 나온 핵심 이슈는 4개다.

1. `누가 대회를 올리는가`가 문서마다 다르게 읽힌다.
2. `허위 대회나 잘못된 링크`를 초기에 막을 운영 장치가 약하다.
3. `포스터 업로드 방식`이 생성과 수정에서 다르다.
4. 사용자 입장에서 중요한 `탐색 필터`가 아직 부족하다.

이 4개는 따로 떨어진 문제가 아니라 서로 연결돼 있다.
예를 들어 사용자 등록을 열면 신고 정책과 관리자 권한이 같이 강해져야 하고, 탐색 기능보다 운영 기능 비중이 커진다.

## 5. 항목별 쉬운 설명

### 5.1 대회 작성 주체가 불명확하다

현재 문서 중 일부는 `사용자가 직접 대회를 등록할 수 있다`는 방향을 전제로 한다.
하지만 서비스 소개와 핵심 기능 설명은 대체로 `대회 정보를 모아 보여주는 탐색 기능`처럼 읽힌다.

이 차이가 중요한 이유는 아래와 같다.

- 서비스 신뢰도 기준이 달라진다
- 앱 UI 범위가 달라진다
- 신고와 검수 정책이 달라진다
- 관리자 권한 범위가 달라진다

쉽게 말하면 선택지는 두 가지다.

### 선택지 A. 큐레이션형 대회 피드

- 운영자 크롤링 + 운영자 수동 등록 중심
- 사용자는 `보기`, `신고`, `외부 신청 링크 이동`만 한다
- 장점은 신뢰도가 높고 운영이 단순하다는 점이다
- 지금 Rolling 단계에 더 잘 맞는다

### 선택지 B. 사용자 게시판형 대회 등록

- 일반 사용자도 대회를 올릴 수 있다
- 장점은 데이터 수집 속도가 빨라질 수 있다는 점이다
- 대신 허위 정보, 중복 등록, 잘못된 포스터, 끊어진 링크 대응이 필요하다
- 운영 검수와 권한 정책이 훨씬 복잡해진다

현재 상태에서는 A와 B가 함께 섞여 있어 기획 기준이 흐려져 있다.

## 5.2 신고 3건 이상 노출 정책은 사용자 등록 대회와 충돌한다

현재 신고 운영은 `같은 대상에 대한 누적 신고가 3건 이상`이어야 관리자 화면에 노출되는 구조다.

이 정책은 `사용자 노이즈를 줄이고 운영 집중도를 높이는 방식`으로는 이해할 수 있다.
하지만 일반 사용자 대회 등록을 여는 순간 문제가 생긴다.

예를 들면:

- 누군가 잘못된 신청 링크를 올린다
- 누군가 이미 끝난 대회를 새 대회처럼 올린다
- 누군가 홍보성 또는 허위 대회를 올린다

이런 경우 대회는 오픈매트처럼 자동 차단되지 않는다.
또 신고가 1건이나 2건일 때는 관리자 기본 화면에서 잘 보이지 않을 수 있다.

즉 지금 구조는 `큐레이션 대회 목록`에는 버틸 수 있어도, `사용자 등록형 대회 게시판`에는 약하다.

사용자 등록을 유지하려면 최소한 아래 중 일부가 먼저 필요하다.

- 관리자 검토를 신고 1건부터 볼 수 있는 경로
- 관리자 숨김 또는 삭제 권한
- 승인 전 노출 보류 상태
- 중복 대회 감지 기준

## 5.3 생성과 수정의 포스터 계약이 다르다

현재 대회 생성은 `posterKey` 기반 업로드 흐름으로 정리돼 있다.
즉:

1. 업로드 URL을 발급받는다
2. 이미지를 S3에 직접 업로드한다
3. 생성 API에는 `posterKey`를 보낸다

그런데 수정은 아직 `posterUrl`을 직접 받는 구조다.

이 차이는 왜 문제인가:

- 프론트가 생성과 수정을 다르게 구현해야 한다
- 운영 문서와 실제 동작이 계속 어긋난다
- 포스터 교체 UX가 애매해진다
- 추후 파일 정리나 권한 관리가 어려워진다

그래서 제품 관점에서는 둘 중 하나가 낫다.

- 수정도 생성과 같은 `posterKey` 계약으로 맞춘다
- 아니면 v1에서는 `포스터 수정` 자체를 닫는다

지금처럼 둘을 혼합한 상태는 장기적으로 유지 비용이 높다.

## 5.4 사용자 문제 정의 대비 대회 필터가 부족하다

서비스 소개를 보면 핵심은 `지역`과 `일정` 기준 탐색 비용을 줄이는 것이다.
그런데 현재 대회 목록 계약은 사용자 관점에서 중요한 필터보다 `source` 중심이다.

`source`는 내부 출처 구분에는 유용하다.
하지만 일반 사용자 입장에서는 보통 아래 정보가 더 중요하다.

- 지금 신청 가능한 대회인지
- 언제 열리는지
- 어느 지역인지
- 어디서 열리는지

즉 현재 상태에서는 `운영 분류 필터`는 있는데 `사용자 탐색 필터`는 약한 편이다.

제품 우선순위상 더 먼저 챙길 만한 것은 아래다.

- 접수 가능 / 마감 필터
- 날짜 기준 정렬과 범위 필터
- 지역 또는 장소 기반 필터
- 검색어 필터

## 6. 그래서 지금 기획은 괜찮은가

완전히 나쁜 기획은 아니다.
오히려 대회 기능의 큰 방향은 맞다.

다만 현재 기획은 아래처럼 보는 게 정확하다.

### 괜찮은 부분

- 오픈매트와 함께 대회 정보를 한곳에 모아 보여주는 방향
- 목록 -> 상세 -> 외부 신청 링크 이동 흐름
- 크롤링 + 수동 등록을 함께 쓰는 구조
- 신고를 공통 도메인으로 묶어 운영 흐름에 연결한 점

### 아직 덜 닫힌 부분

- 일반 사용자 대회 등록을 지금 열지
- 관리자에게 어느 정도 수정/삭제 권한을 줄지
- 신고를 몇 건부터 운영이 볼지
- 대회 탐색 필터를 무엇부터 제공할지
- 포스터 수정 계약을 어떻게 통일할지

즉 `탐색 기능`으로 보면 괜찮고,
`게시판형 기능`으로 보면 아직 준비가 덜 된 상태다.

## 7. 제품 권장안

### 지금 출시 권장 범위

- 대회 목록 조회
- 대회 상세 조회
- 외부 신청 링크 이동
- 크롤링 등록
- 운영자 수동 등록
- 사용자 신고
- 접수 가능 여부 중심 정렬
- 날짜 / 지역 / 상태 중심 필터 강화

### 다음 단계 권장 범위

- 관리자 숨김 또는 삭제 권한 정리
- 신고 1건부터 확인 가능한 운영 경로 추가
- 대회 포스터 수정 계약 통일
- 중복 등록 방지 기준 강화

### 나중에 열어도 되는 범위

- 일반 사용자 대회 등록
- 일반 사용자 대회 수정
- 일반 사용자 대회 삭제
- 승인 대기 / 검수 완료 / 숨김 같은 상태 추가

## 8. 지금 가장 먼저 결정해야 하는 질문

아래 질문 3개가 먼저 정해져야 나머지 정책이 자연스럽게 정리된다.

1. 대회는 `큐레이션 피드`인가, `사용자 게시판`인가
2. 사용자가 대회를 올릴 수 있다면 `검수 전 공개`인가, `검수 후 공개`인가
3. 운영자는 다른 사람이 올린 대회를 `숨김/삭제`할 수 있어야 하는가

이 3개가 정해지지 않으면 신고 정책, 권한 정책, 앱 UI, 문서가 계속 흔들리게 된다.

## 9. 최종 결론

현재 Rolling의 대회 기능은 `탐색 중심 기능`으로는 충분히 좋은 방향이다.
하지만 `일반 사용자 등록형 기능`까지 지금 같이 가져가면 운영 리스크가 커진다.

따라서 현재 단계의 추천 결론은 아래와 같다.

- 지금은 `운영 중심 큐레이션형 대회 기능`으로 고정한다
- 사용자 가치는 `탐색 필터 강화`에서 먼저 만든다
- 신고와 관리자 권한이 정리되기 전까지는 사용자 등록은 뒤로 미룬다
- 포스터 수정 계약은 생성과 같은 방식으로 통일하거나 일단 닫는다

이 방향이 현재 서비스 목표와 운영 현실을 가장 잘 맞춘다.
