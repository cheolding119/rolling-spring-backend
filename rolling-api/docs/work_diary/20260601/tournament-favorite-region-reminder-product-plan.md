# 대회 찜/지역/마감 알림 기획서

## 1. 문서 목적

- 이 문서는 2026-06-01 기준 운영 중인 `rolling-api`에서 대회 도메인에 `찜`, `지역`, `접수 마감 전 푸시 알림`을 추가하기 위한 제품 초안이다.
- 목표는 현재 운영 중인 대회 조회 흐름을 깨지 않으면서, 사용자가 관심 대회를 저장하고 다시 찾고, 접수 마감 전에 알림을 받을 수 있게 만드는 것이다.
- 이 문서는 구현 상세보다 제품 범위, 우선순위, 운영 리스크, 수용 기준, 미해결 의사결정을 먼저 정리한다.

## 2. 현재 상태

### 2.1 현재 구현 범위

- 현재 대회 도메인은 목록 조회, 상세 조회, 등록, 수정, 삭제, 신고, 크롤링 중심으로 동작한다.
- 공개 API는 `GET /api/v1/tournaments`, `GET /api/v1/tournaments/{id}`다.
- 목록 필터는 현재 `source`만 지원한다.
- 응답 필드는 `title`, `organizer`, `posterUrl`, `competitionDate`, `registrationDeadline`, `location`, `applyLink`, `registrationClosed` 중심이다.
- 현재 대회에는 `region`, `favorite`, `reminder` 개념이 없다.

### 2.2 현재 운영 제약

- 현재 `registrationDeadline`은 `LocalDate` 기준 `YYYY-MM-DD`만 저장한다.
- 즉 현재 데이터만으로는 "실제 접수 종료 시각"을 정확히 알 수 없다.
- 현재 `location`은 자유 텍스트라서, `경기`, `경남`, `대구` 같은 지역 분류를 안정적으로 필터하려면 별도 필드가 필요하다.
- 현재 대회 목록은 전체 조회 후 메모리에서 필터/정렬/페이징하는 구조라, 개인화 로직을 무겁게 넣으면 성능 리스크가 커질 수 있다.

### 2.3 재사용 가능한 기존 자산

- 오픈매트/세미나는 이미 `Region` enum을 사용한다.
- 앱 전체에는 `Notification` 저장 + FCM 발송 시도 패턴이 이미 있다.
- 사용자 전역 푸시 설정 `pushNotificationEnabled`가 존재한다.
- 스케줄러 헬스체크와 실패 모니터링 기반이 이미 있다.

## 3. 해결하려는 사용자 문제

### 3.1 탐색 문제

- 사용자는 대회를 찾을 때 `서울 강남구 ...` 같은 주소보다 `경기`, `경남`, `대구`처럼 넓은 지역 단위로 먼저 좁히고 싶다.
- 현재는 `location` 문자열만 있어 지역별 탐색이 어렵다.

### 3.2 재방문 문제

- 사용자는 나중에 접수할 대회를 저장해두고 다시 보고 싶다.
- 현재는 관심 대회를 따로 모아보는 기능이 없다.

### 3.3 마감 놓침 문제

- 사용자는 관심 대회의 접수 마감을 자주 놓칠 수 있다.
- 현재는 접수 마감 전 사용자별 리마인드 수단이 없다.

## 4. 제품 목표

### 4.1 사용자 목표

- 사용자는 대회를 `지역` 기준으로 더 쉽게 탐색할 수 있어야 한다.
- 사용자는 관심 대회를 `찜`하고, 찜한 대회만 다시 모아볼 수 있어야 한다.
- 사용자는 접수 마감 전에 원하는 시점에 리마인드 푸시를 받을 수 있어야 한다.

### 4.2 비즈니스/운영 목표

- 기존 공개 조회 흐름을 깨지 않는다.
- 비회원 조회와 기존 앱 버전 동작에 영향을 주지 않는다.
- 푸시 발송 실패가 대회 조회, 찜 저장, 앱 핵심 사용 흐름을 막지 않게 한다.
- 운영자가 장애 원인을 지역 필드, 찜 데이터, 리마인드 스케줄러 중 어디인지 분리해서 볼 수 있어야 한다.

## 5. 권장 범위

### 5.1 최종 목표 범위

| 영역 | 기능 |
| --- | --- |
| 분류 | 대회 `region` 저장 및 필터 |
| 찜 | 찜 추가 / 해제 |
| 찜 | 찜한 대회 목록 조회 |
| 알림 | 찜한 대회별 마감 전 리마인드 설정 |
| 알림 | 설정된 시각에 Notification 저장 및 FCM 발송 시도 |

### 5.2 지금 출시할 범위 권장안

운영 안정성을 우선하면 1차는 아래 범위가 적절하다.

| 영역 | 기능 | 이유 |
| --- | --- | --- |
| 분류 | `region` 필드 추가 | 사용자 탐색 가치가 크고 운영 리스크가 낮다 |
| 조회 | `region` 필터 추가 | 기존 공개 목록 계약에 optional query만 추가하면 된다 |
| 찜 | 찜 추가 / 해제 | 사용자 가치가 높고 쓰기 모델이 단순하다 |

| 알림 | 찜한 대회 1건당 리마인드 1개 설정 | 즐겨찾기 레코드에 상태와 시각을 함께 저장하면 단순하다 |
| 알림 | 설정 시각 도래 시 Notification 저장 + FCM 발송 시도 | 기존 알림 인프라를 재사용할 수 있다 |
| 상태 동기화 | 마감일 변경/삭제 시 리마인드 재계산 또는 취소 | 운영 일관성을 보장해야 한다 |

### 5.3 다음 출시 범위 권장안

2차에서 아래 범위를 여는 것을 권장한다.

| 영역 | 기능 | 이유 |
| --- | --- | --- |
| 알림 | 대회 1건당 다중 리마인드 | 1차는 1건 1리마인드로 제한하는 것이 안전하다 |
| 알림 | 리마인드 수정 이력 및 고급 운영 로그 | 1차 운영 안정화 후 필요성을 판단한다 |
| 개인화 | 목록 응답의 `favorited` 기본 포함 | 목록 성능 검증이 선행되어야 한다 |

### 5.4 나중에 검토할 범위

- 찜 기반 추천 대회
- 캘린더 연동
- 실제 `registrationDeadlineAt` 기반 정밀 마감 알림

## 6. 핵심 권장안

### 6.1 지역 모델

- 오픈매트/세미나에서 이미 쓰는 `Region` enum을 재사용하는 것이 맞다.
- 새 자유 텍스트 카테고리를 만들지 않는다.
- `region`은 `SEOUL`, `GYEONGGI`, `GYEONGNAM`, `DAEGU` 같은 표준 enum 값을 사용한다.

권장 이유:

- 도메인 간 지역 기준이 통일된다.
- 앱 필터 UI와 백엔드 raw value를 재활용할 수 있다.
- 운영자가 지역 값 품질을 관리하기 쉽다.

### 6.2 지역 필드 추가 방식

- `tournaments.region`은 1차에 nullable로 추가한다.
- 수동 등록 대회는 새 앱/관리자 화면부터 `region` 입력을 받는다.
- 크롤링 대회는 region을 수집하거나 자동 추론하지 않는다.
- 크롤링 이후 운영자가 region을 수동으로 입력하거나 보정하는 것을 기본 정책으로 둔다.

권장 이유:

- 운영 배포 시 대량 backfill 실패가 핵심 흐름을 막지 않는다.
- 잘못된 자동 분류보다 운영자 수동 입력이 안전하다.

### 6.3 찜 모델

- `tournament_favorites` 같은 별도 테이블로 사용자-대회 관계를 저장한다.
- `UNIQUE(user_id, tournament_id)`를 둔다.
- 찜은 인증 사용자만 가능하다.
- 즐겨찾기 레코드에 아래 알림 필드를 함께 둔다.

| 필드 | 의미 |
| --- | --- |
| `notificationEnabled` | 알림 on/off 상태 |
| `remindDate` | 알림 발송 날짜 |
| `remindTime` | 알림 발송 시간 |
| `scheduledAt` | 스케줄러 실행용 계산 시각 |
| `sentAt` | 실제 발송 완료 시각 |

- 찜 해제 시 리마인드도 함께 비활성화하거나 삭제한다.

### 6.4 리마인드 모델

- 리마인드는 "찜한 대회에만 설정 가능"으로 묶는 것이 맞다.
- 1차 발송 범위는 "대회 1건당 사용자 1개 리마인드"로 제한하는 것이 맞다.
- 알림 상태는 `on/off`로 명확히 저장한다.
- 알림 시각은 프리셋 코드가 아니라 `날짜 + 시간`으로 저장한다.
- 프론트는 날짜 선택 시 `마감일 기준 D-1`, `D-2`, `D-30` 같은 빠른 선택값을 제공할 수 있다.
- 예를 들어 접수 마감일이 `2026-06-14`이면 `1일 전`을 누를 때 `remindDate=2026-06-13`이 선택된다.
- 시간은 별도 time picker로 선택하고, 예를 들어 `09:00`을 고르면 최종 발송 시각은 `2026-06-13T09:00:00` KST가 된다.
- 서버는 `remindDate + remindTime`으로 `scheduledAt`을 계산해 저장한다.

권장 이유:

- 프론트가 D-1 같은 빠른 선택 UX를 제공하면서도 실제 저장값은 명확한 날짜/시간이 된다.
- 현재 `registrationDeadline`이 날짜 단위여도 서버 계산이 가능하다.
- 서버는 `scheduledAt <= now` 기준으로 단순 발송하면 된다.
- 다중 리마인드보다 중복 발송, 상태 관리, UX가 단순하다.

### 6.5 마감 시점 정책

- 현재 `registrationDeadline`이 날짜만 있으므로, 1차 정책은 `registrationDeadline` 당일 `23:59:59` KST를 내부 기준 마감 시점으로 본다.
- 사용자가 선택한 `remindDate + remindTime`은 이 내부 마감 기준 시점보다 이전이어야 한다.
- 단, 사용자 문구는 "앱에 저장된 마감일 기준 알림"으로 표현하는 것이 안전하다.
- 크롤링 원본 사이트의 실제 마감 시각과 차이가 날 수 있다는 점을 운영 메모에 남긴다.

권장 이유:

- 현재 DB 스키마를 크게 흔들지 않고 리마인드를 설계할 수 있다.
- 정확한 시각 데이터가 없는 상황에서 가장 일관된 기준이다.

## 7. 추천 사용자 흐름

### 7.1 지역 탐색

1. 사용자는 대회 목록에 진입한다.
2. `region` 필터에서 `경기`, `경남`, `대구` 등 지역을 선택한다.
3. 서버는 `region`이 일치하는 대회를 우선 반환한다.

### 7.2 대회 찜

1. 로그인 사용자는 대회 상세 또는 찜 가능한 UI에서 찜을 누른다.
2. 이미 찜한 대회면 중복 생성하지 않는다.
3. 찜 성공 후 사용자는 마이페이지 또는 별도 탭에서 찜한 대회 목록을 조회한다.

### 7.3 마감 리마인드

1. 사용자는 찜한 대회에서 알림 스위치를 `on`으로 바꾼다.
2. 프론트는 날짜를 선택하게 하고, 필요하면 `1일 전`, `2일 전`, `30일 전` 같은 빠른 선택 버튼으로 `remindDate`를 채운다.
3. 시간은 time picker로 선택한다.
4. 서버는 `notificationEnabled`, `remindDate`, `remindTime`으로 `scheduledAt`을 계산하고, 현재 시각 이후인지 검증한다.
4. 시각이 도래하면 Notification 저장을 먼저 수행한다.
5. FCM 발송은 시도하되 실패해도 핵심 트랜잭션을 실패시키지 않는다.

## 8. API 범위 권장안

### 8.1 목록/상세

- `GET /api/v1/tournaments?region=GYEONGGI`
- 상세/목록 응답에는 우선 `region`을 추가한다.

추가 고려:

- `favorited`를 목록 응답 전체에 바로 넣으면 개인화 쿼리 비용이 늘 수 있다.
- 1차는 `찜 목록 API`와 `상세` 위주로 시작하고, 목록 개인화는 성능 확인 후 붙이는 것이 안전하다.

### 8.2 찜 API

- `POST /api/v1/tournaments/{id}/favorite`
- `DELETE /api/v1/tournaments/{id}/favorite`
- `GET /api/v1/tournaments/favorites`

권장 원칙:

- 찜 추가는 멱등적으로 처리한다.
- 삭제된 대회는 찜 추가를 막는다.
- 하드 삭제 시 찜 데이터는 함께 정리한다.

### 8.3 리마인드 API

이번 출시 권장 예시:

- `PATCH /api/v1/tournaments/{id}/favorite-reminder`

요청 예시:

```json
{
  "notificationEnabled": true,
  "remindDate": "2026-06-13",
  "remindTime": "09:00"
}
```

권장 검증:

- 찜한 대회만 설정 가능
- `notificationEnabled=true`이면 `remindDate`, `remindTime`이 모두 필요함
- `remindDate + remindTime`으로 계산한 `scheduledAt`은 현재 시각 이후여야 함
- `remindDate + remindTime`으로 계산한 `scheduledAt`은 내부 마감 기준 시점 이전이어야 함
- 계산 결과가 과거면 저장 불가
- 이미 접수 마감된 대회는 설정 불가
- `notificationEnabled=false`이면 날짜/시간을 비워두거나 기존 값을 무시하는 정책이 필요함

## 9. 운영 안정성 원칙

### 9.1 파괴적 변경 금지

- 기존 목록/상세 API 의미를 바꾸지 않는다.
- 새 query parameter는 optional로 추가한다.
- 새 컬럼은 nullable 또는 신규 테이블 방식으로 추가한다.

### 9.2 공개 조회와 개인화 쓰기 분리

- 비회원 공개 조회는 계속 동작해야 한다.
- 찜/리마인드는 인증 사용자 전용으로 분리한다.
- 목록 전체를 강하게 개인화하기보다 별도 찜 목록 흐름으로 시작한다.

### 9.3 알림 실패 분리

- 알림 inbox 저장과 FCM 발송을 분리한다.
- FCM 실패는 조회/찜/리마인드 저장을 롤백시키지 않는다.
- 스케줄러 실패는 운영 알림으로 드러나야 한다.

### 9.4 지역 입력 운영 원칙

- 크롤링은 region을 수집하지 않는다.
- region은 운영자가 수동으로 입력하거나 수정한다.
- 크롤링 직후 region이 비어 있어도 공개 조회는 계속 동작해야 한다.

## 10. 리스크와 완화

| 리스크 | 영향 | 완화 |
| --- | --- | --- |
| `registrationDeadline`이 날짜만 있음 | "정확한 마감 시각 전 알림" 보장 어려움 | 1차는 KST 당일 23:59 기준으로 정의 |
| 대회 목록 개인화 과부하 | 목록 성능 악화 | 1차는 찜 목록 API 중심, 목록 개인화는 후속 검증 |
| 운영자가 region을 입력하지 않음 | 지역 필터 누락 또는 품질 저하 | region 미입력 대회 노출 정책과 운영 입력 절차를 함께 둔다 |
| 리마인드 중복 발송 | 사용자 불만, 운영 이슈 | 1건 1리마인드, `sentAt`/상태 컬럼, 멱등 처리 |
| 이미 지난 날짜/시간 선택 | 저장 직후 발송 또는 validation 혼란 | 서버 검증 + 프론트 제한 처리 |
| 대회 마감일 변경 후 잘못된 알림 | 신뢰도 하락 | 마감일 수정 시 pending reminder 재검증 |
| 푸시 토큰 없음 또는 전역 푸시 OFF | 알림 미수신 | Notification 저장은 유지, 푸시는 best effort |
| 대회 삭제와 찜 데이터 불일치 | 오류 또는 고아 데이터 | 하드 삭제 시 찜/리마인드 cascade 정리 |

## 11. 성공 신호

- 지역 필터 사용률이 확인된다.
- 찜 추가율과 찜 목록 재방문율이 나온다.
- 찜 후 실제 상세 재방문 또는 외부 접수 링크 클릭률이 증가한다.
- 리마인드 설정 사용률과 발송 성공률을 분리해서 볼 수 있다.
- 접수 마감 놓침 관련 CS 또는 문의가 줄어든다.

## 12. 수용 기준

### 12.1 1차

- `region` 없는 기존 대회도 계속 조회된다.
- `region` query가 없으면 기존 목록 결과와 의미가 동일하다.
- 로그인 사용자는 대회를 찜/해제할 수 있다.
- 사용자는 찜한 대회 목록을 조회할 수 있다.
- 찜한 대회에만 리마인드를 설정할 수 있다.
- 즐겨찾기 레코드에 `notificationEnabled` 상태가 저장된다.
- `notificationEnabled=true`일 때 날짜와 시간이 함께 저장된다.
- 계산한 `scheduledAt`이 과거면 저장할 수 없다.
- 리마인드 시각 도래 시 Notification 저장이 이뤄진다.
- FCM 실패가 있어도 리마인드 작업 전체가 실패 처리되지 않는다.
- 동일 리마인드가 중복 발송되지 않는다.
- 비회원 공개 조회는 그대로 동작한다.

### 12.2 2차

- 다중 리마인드 정책이 추가되더라도 기존 날짜/시간 저장 계약이 깨지지 않는다.
- 목록 응답에 `favorited`를 붙여도 성능 기준이 유지된다.

## 15. 최종 권장 결론

- 2026-06-01 기준 이번 출시에서 리마인드까지 포함하려면, 즐겨찾기 레코드에 `알림 on/off + 알림 날짜 + 알림 시간`을 저장하는 방식이 가장 명확하다.
- 지역 분류는 새 체계를 만들기보다 기존 `Region` enum을 재사용하는 것이 맞다.
- region은 크롤링에서 자동 수집하지 않고 운영자가 직접 입력하는 정책으로 가는 것이 맞다.
- 리마인드는 프론트가 `1일 전`, `2일 전`, `30일 전` 같은 빠른 날짜 선택 UX를 줄 수 있지만, 서버 저장값은 최종적으로 `날짜 + 시간 + scheduledAt`이어야 한다.
- 현재 `registrationDeadline`이 날짜만 저장된다는 점이 가장 큰 제품 제약이므로, 문구와 정책을 먼저 명확히 정한 뒤 구현에 들어가는 것이 맞다.
