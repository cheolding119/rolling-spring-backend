# 관리자 사용자 차단 기능 기획서

## 1. 문서 목적

관리자가 운영 이슈가 있는 사용자를 서비스 차원에서 차단하고, 차단 상태를 해제하며, 처리 이력을 추적할 수 있는 기능을 정의한다.

본 문서는 관리자용 사용자 차단 기능의 정책, 데이터 구조, API, 운영 흐름, 개발 범위를 정리한다.

## 2. 배경

현재 코드 기준으로 확인된 사항은 다음과 같다.

- 관리자 운영 기능은 신고 관리, 오픈매트 신고 차단 해제 등 일부 기능만 존재한다.
- 특정 사용자를 서비스 전반에서 이용 불가 상태로 만드는 관리자 기능은 없다.

즉, 신고 누적 또는 운영 판단에 따라 문제 사용자를 즉시 제한할 수 있는 계정 단위 제재 기능이 필요하다.

## 3. 목표

- 관리자가 특정 사용자를 즉시 차단할 수 있어야 한다.
- 차단된 사용자는 인증 기반 주요 기능을 사용할 수 없어야 한다.
- 이미 발급된 토큰이 있어도 차단 이후 API 접근이 막혀야 한다.
- 차단 사유, 메모, 처리자, 처리 시각이 기록되어야 한다.
- 기간 차단과 영구 차단을 모두 지원할 수 있어야 한다.
- 차단 해제 이력도 함께 남겨야 한다.

## 4. 비목표

아래 항목은 본 기능의 1차 범위에 포함하지 않는다.

- 사용자 신고 대상 타입을 별도 `USER` 로 확장하는 기능
- 차단과 동시에 해당 사용자의 게시물, 오픈매트, 대회 글을 자동 삭제하는 기능
- 고객센터 워크플로우 자동화
- 법무, 환불, 정산 정책 자동화

## 5. 용어 정의

### 5.1 관리자 차단

운영자가 특정 사용자 계정을 서비스 차원에서 제한하는 기능이다. 이번 기능의 핵심 대상이다.

### 5.2 영구 차단

해제 전까지 만료 시점 없이 유지되는 차단 상태이다.

### 5.3 기간 차단

`blockedUntil` 시각까지 유지되는 차단 상태이다. 만료 시 자동 또는 요청 시점 판별로 해제된다.

## 6. 핵심 정책

### 6.1 계정 상태 정책

사용자 계정은 아래 상태 중 하나를 가진다.

- `ACTIVE`: 정상 이용 가능
- `BLOCKED`: 관리자 차단 상태
- `WITHDRAWN`: 탈퇴 상태

### 6.2 차단 효과

차단된 사용자는 아래 동작이 제한된다.

- 로그인
- 토큰 재발급
- 내 정보 조회 및 수정
- 오픈매트 생성, 수정, 삭제, 신청, 취소
- 신고 등록
- 기타 인증이 필요한 API 호출 전반

### 6.3 즉시 반영 정책

차단 이후에는 기존 access token 이 남아 있어도 다음 API 요청부터 차단되어야 한다.

즉, 인증 단계 또는 사용자 조회 공통 로직에서 차단 여부를 검사해야 한다.

### 6.4 예외 정책

- 관리자는 자기 자신을 차단할 수 없다.
- 탈퇴 사용자는 차단 대상이 아니다.
- 존재하지 않는 사용자는 차단할 수 없다.
- 이미 차단된 사용자를 다시 차단할 경우 정책을 명확히 정의해야 한다.

권장 정책은 다음과 같다.

- 이미 차단된 상태에서 재차단 요청이 들어오면 차단 정보를 갱신한다.
- 다만 운영 이력에는 별도의 `BLOCK` 이벤트를 추가로 남긴다.

## 7. 운영 정책 제안

### 7.1 MVP 운영 원칙

1차 버전에서는 계정 차단과 콘텐츠 조치를 분리한다.

즉, 사용자 차단은 계정 접근 제한만 담당하고, 해당 사용자가 작성한 오픈매트나 다른 콘텐츠의 숨김 또는 삭제는 운영자가 별도 판단 후 수행한다.

### 7.2 분리 이유

- 현재 코드 구조상 콘텐츠 도메인 영향 범위가 크다.
- 자동 숨김까지 함께 넣으면 운영 정책 충돌 가능성이 높다.
- 계정 차단만 우선 구현하면 기능 도입 속도와 안정성이 높다.

- 현재 계정 상태
- 차단 여부와 차단 정보
- 차단 처리자
- 차단 시작일시
- 차단 종료일시
- 차단 사유

- 차단 사유 입력 필수

- 처리자 정보 자동 기록
- 처리 시각 자동 기록

### 8.4 관리자 사용자 차단 해제

### 8.5 관리자 사용자 차단 이력 조회

- 누가 언제 어떤 사유로 조치했는지 조회 가능

## 9. 데이터 모델 제안

### 9.1 설계 방향

차단 메타데이터를 모두 `users` 테이블에 넣는 방식은 권장하지 않는다.

이유는 다음과 같다.

- `users` 테이블 책임이 과도하게 커진다.
- 차단 관련 컬럼이 계속 늘어날 가능성이 높다.
- 현재 상태와 이력성 데이터를 한 테이블에 함께 넣게 된다.
- 향후 제재 정책이 확장되면 스키마 변경 비용이 커진다.

권장안은 다음과 같다.

- `users`: 계정의 현재 상태만 보관
- `user_account_blocks`: 현재 적용 중인 관리자 차단 상세 정보 보관
- `user_sanction_histories`: 관리자 제재 이력 보관

### 9.2 users 테이블 최소 확장

`users` 테이블에는 아래 컬럼만 추가하는 것을 권장한다.

- `account_status`

### 컬럼 의미

- `account_status`: 현재 계정 상태. `ACTIVE`, `BLOCKED`, `WITHDRAWN`

### 최소 확장 권장 이유

- 인증 단계에서 빠르게 차단 여부를 판별할 수 있다.
- 매 요청마다 차단 상세 테이블을 조인하지 않아도 된다.
- 현재 계정 상태와 운영 메타데이터를 분리할 수 있다.

### 9.3 현재 차단 상세 테이블 추가

별도 테이블 `user_account_blocks` 추가를 권장한다.

예상 컬럼은 다음과 같다.

- `id`
- `user_id`
- `blocked_at`
- `blocked_until`
- `reason`
- `memo`
- `blocked_by_user_id`
- `created_at`
- `updated_at`

### 테이블 역할

- 현재 유효한 관리자 차단 정보 1건을 보관한다.
- 영구 차단과 기간 차단 모두 표현한다.
- 관리자 상세 화면과 차단 응답 데이터의 원본이 된다.

### 운영 제약 권장

- 사용자당 활성 차단 정보는 최대 1건만 유지한다.
- 재차단 시 기존 행을 갱신하거나, 종료 후 새 행을 생성하는 정책 중 하나를 선택한다.

권장 정책은 다음과 같다.

- 현재 차단 상태는 `user_account_blocks` 에 1건만 유지
- 모든 변경 이력은 `user_sanction_histories` 에 누적 저장

### 9.4 이력 테이블 추가

별도 이력 테이블 `user_sanction_histories` 추가를 권장한다.

예상 컬럼은 다음과 같다.

- `id`
- `user_id`
- `action` (`BLOCK`, `UNBLOCK`, `AUTO_RELEASE`)
- `reason`
- `memo`
- `processed_by_user_id`
- `created_at`

### 이력 테이블 필요 이유

- 현재 상태만으로는 운영 판단 근거를 추적할 수 없다.
- 관리자 기능은 감사 로그 성격의 기록이 필요하다.
- 차단 정보가 갱신되는 경우에도 이전 조치 히스토리를 보존해야 한다.

## 10. API 제안

### 10.1 관리자 사용자 목록 조회

- `GET /api/v1/admin/users`

#### query parameter 예시

- `status`
- `keyword`
- `page`
- `size`
- `sort`

### 10.2 관리자 사용자 상세 조회

- `GET /api/v1/admin/users/{id}`

### 10.3 관리자 사용자 차단

- `PATCH /api/v1/admin/users/{id}/block`

#### request body 예시

```json
{
  "type": "TEMPORARY",
  "blockedUntil": "2026-04-30T23:59:59",
  "reason": "반복적인 허위 홍보 및 신고 누적",
  "memo": "4월 운영 회의 결정 사항 반영"
}
```

### 10.4 관리자 사용자 차단 해제

- `PATCH /api/v1/admin/users/{id}/unblock`

#### request body 예시

```json
{
  "memo": "오인 차단 확인 후 해제"
}
```

### 10.5 관리자 사용자 제재 이력 조회

- `GET /api/v1/admin/users/{id}/sanctions`

## 11. 응답 정책

### 11.1 차단 성공 응답

관리자 차단, 해제 API는 대상 사용자의 최신 상태를 응답으로 반환한다.

예시 필드는 다음과 같다.

- `id`
- `nickname`
- `accountStatus`
- `blocked`
- `blockedAt`
- `blockedUntil`
- `blockedReason`
- `blockedByUserId`

### 11.2 차단 사용자 접근 실패 응답

차단된 사용자가 인증 기반 API를 호출하면 아래 형식의 오류를 반환한다.

```json
{
  "success": false,
  "code": "USER_BLOCKED",
  "message": "관리자에 의해 서비스 이용이 제한되었습니다",
  "data": {
    "blockedUntil": "2026-04-30T23:59:59"
  }
}
```

영구 차단인 경우 `blockedUntil` 은 `null` 이다.

## 12. 예외 처리 정책

- 자기 자신 차단 요청: `400`
- 존재하지 않는 사용자: `404`
- 탈퇴 사용자 차단 요청: `400` 또는 `404`
- 기간 차단인데 `blockedUntil` 누락: `400`
- 기간 차단인데 `blockedUntil` 이 현재보다 과거: `400`
- 차단되지 않은 사용자 해제 요청: `400`

권장 에러 코드는 다음과 같다.

- `USER_BLOCKED`
- `USER_ALREADY_BLOCKED`
- `USER_NOT_BLOCKED`
- `SELF_BLOCK_NOT_ALLOWED`
- `INVALID_BLOCK_PERIOD`

## 13. 사용자 앱 동작 요구사항

- 로그인 시 차단된 계정이면 차단 안내 화면으로 이동
- 차단된 계정의 토큰 재발급 요청도 실패 처리
- 인증 API 호출 시 `USER_BLOCKED` 수신하면 재로그인 유도 대신 차단 안내를 우선 표시
- 영구 차단이면 고객센터 문의 문구 노출
- 기간 차단이면 해제 예정 시각 노출

## 14. 운영 시나리오

### 시나리오 1. 신고 누적 사용자 차단

1. 관리자가 신고 운영 화면에서 문제 사용자를 확인한다.
2. 사용자 상세에서 계정 상태와 운영 이력을 조회한다.
3. 차단 사유와 메모를 입력해 차단한다.
4. 시스템은 계정 상태를 `BLOCKED` 로 변경한다.
5. 이후 해당 사용자의 인증 API 호출은 즉시 차단된다.
6. 처리 이력이 저장된다.

### 시나리오 2. 오인 차단 해제

1. 관리자가 사용자 상세에서 오인 차단 여부를 확인한다.
2. 차단 해제 요청을 수행한다.
3. 시스템은 계정 상태를 `ACTIVE` 로 변경한다.
4. 해제 이력이 저장된다.

### 시나리오 3. 기간 차단 만료

1. 기간 차단 사용자의 `blockedUntil` 시각이 경과한다.
2. 스케줄러 또는 요청 시점 검사에서 만료를 감지한다.
3. 계정 상태를 `ACTIVE` 로 복구한다.
4. `AUTO_RELEASE` 이력을 저장한다.

## 15. 개발 설계 권장 사항

### 15.1 상태 모델 분리

관리자 차단 정보는 계정 기본 정보와 분리해 관리한다.

권장 방식은 다음과 같다.

- `users`: 현재 계정 상태
- `user_account_blocks`: 현재 차단 상세
- `user_sanction_histories`: 차단, 해제 이력

### 15.2 공통 사용자 조회 로직 반영

현재 서비스 레이어의 활성 사용자 조회는 탈퇴 여부만 확인한다.

관리자 차단 기능 도입 후에는 다음 중 하나를 적용해야 한다.

- 공통 `getActiveUser()` 가 차단 여부까지 검사
- 또는 인증 이후 공통 가드에서 차단 여부를 검사

### 15.3 JWT 필터 반영

이미 발급된 토큰을 즉시 무력화하려면 JWT 인증 단계에서 차단 여부를 확인해야 한다.

즉, 현재의 “withdrawn 아님” 검사를 “withdrawn 아님 + account_status != BLOCKED”로 확장하는 방향이 적절하다.

### 15.4 만료 처리 전략

기간 차단 해제는 아래 2가지 중 하나를 사용한다.

- 스케줄러 기반 자동 해제
- 요청 시점 만료 판별 후 lazy release

권장 순서는 다음과 같다.

1. 1차 릴리스: 요청 시점 만료 판별
2. 2차 릴리스: 스케줄러 기반 자동 해제 추가

- JWT 인증 단계 차단 검사 추가
- 주요 서비스 공통 사용자 조회 차단 검사 추가

### 16.2 2차 개발

### 16.3 3차 개발

- 기간 차단 자동 해제 스케줄러
- 신고 운영 화면과 사용자 차단 기능 연동 강화
- 운영 메모 검색 및 통계 기능

## 17. 테스트 항목

- 관리자만 차단, 해제 API 호출 가능
- 일반 사용자는 관리자 API 호출 불가
- 차단된 사용자는 로그인 불가
- 차단된 사용자는 토큰 재발급 불가
- 차단된 사용자는 주요 인증 API 호출 불가
- 기간 차단 종료 후 정상 접근 가능
- 자기 자신 차단 불가
- 탈퇴 사용자 차단 불가
- 차단, 해제 이력 정상 저장

## 18. 결론

관리자 사용자 차단 기능은 신고 운영 기능의 다음 단계로 필요한 핵심 운영 기능이다.

1차 구현은 계정 상태 관리, 차단, 해제 API, 인증 차단, 이력 저장에 집중하는 것이 가장 현실적이다.  
콘텐츠 자동 숨김이나 신고 대상 확장 같은 기능은 이후 단계로 분리하는 것이 현재 코드 구조와 운영 안정성 측면에서 적절하다.
